# 17. 검증 함정 · 디버깅 로그 (문제 발견 → 해결)

> 이 프로젝트에서 **잘못될 뻔한 것을 알아채고 고친 기록**. 최종 숫자보다 이 과정이 중요하다 —
> "완벽한 결과"를 의심하고, 평가가 공정한지 따지고, 피처가 진짜 신호만 담는지 검증한 흔적.
> 각 항목: 증상 → 원인 → 해결 → 교훈.

## #1 ★ "완벽한 점수"의 함정 — 평가셋에 정상이 없었다

**증상.** CSIC 교차검증에서 수치가 너무 좋았다:

```
방법        TP   FP   FN  TN  Precision Recall  F1
iforest   1105   0  149   0    1.00    0.88   0.94
lof       1254   0    0   0    1.00    1.00   1.00
autoencoder 1254 0    0   0    1.00    1.00   1.00
```

**이상 신호.** `TN=0`, `FP=0`. 정상(negative) 표본이 평가셋에 **하나도 없다**는 뜻. 그러면 "정상을 공격이라 잘못 부를" 기회 자체가 없어 **Precision=1.00은 공짜**다. 의미 있는 건 Recall뿐.

**원인.** `--train-until 2026-01-02`가 **정상 전부(2026-01-01)를 학습**으로 보냈고, `evaluate.py`는 학습 밖(test) 구간만 채점한다 → 평가셋 = 공격만.

**해결.** `ml/load_csic.py`에 `--normal-test-frac`(기본 0.3) 추가 → 정상의 일부를 평가셋(day02)에 **남겨서** 공격과 함께 채점. 이제 FP·Precision이 실제로 측정된다.

```bash
python ml/load_csic.py ... --normal-test-frac 0.3   # 평가셋 = 정상 일부 + 공격
```

**고치기 전 → 고친 뒤 (같은 CSIC 데이터, 내용 피처):**

| | TN | FP | Precision | Recall(LOF) |
|---|---|---|---|---|
| 전(정상 0개 평가) | 0 | 0 | **1.00(가짜)** | 1.00 |
| 후(정상 ~540개 평가) | 485 | 55 | **0.96(진짜)** | 1.00 |

고친 뒤 실제 수치: iforest P0.95/R0.88/F0.91, lof P0.96/R1.00/F0.98, autoencoder P0.96/R1.00/F0.98. 정상 540개 중 오탐 ~55개(≈10%)는 `contamination=0.1` 설정 그대로다(docs/13 E3). 낮추려면 `--contamination 0.05`.

**교훈.**
- **완벽한 점수(1.00)는 축하가 아니라 의심 신호다.** 먼저 평가셋 구성을 본다.
- Precision은 **평가셋에 정상이 있어야** 의미가 있다. `TN=0`이면 Precision은 읽지 않는다.
- 탐지율(Recall)과 오탐률(FP/Precision)은 **항상 함께** 봐야 한다 — 하나만 좋은 건 함정일 수 있다.

## #2 피처가 정상까지 공격처럼 보이게 함 — `uniq_objects`

**증상.** 정상 로그인데 `uniq_objects`가 52까지 나와 공격(BOLA)과 구분이 안 됨.

**원인.** 경로의 **모든 숫자**를 객체 id로 셌다 → 정상 사용자가 상품을 여러 개 구경만 해도(`/products/1,7,23…`) 값이 치솟음. 상품은 **공개 자원**이라 BOLA 신호가 아니다.

**해결.** "주인만 봐야 하는 자원"(장바구니·주문·회원)의 id만 세도록 제한 (`OWNED_PREFIXES`, `--owned-path`). DB도 동일(`OWNED_TABLES`).

**교훈.** 피처는 **공격 신호만** 담아야 한다. 정상 행동이 같은 피처를 올리면 그 피처는 공격·정상을 못 가른다. (공개 자원 vs 소유 자원 구분)

## #3 정규식이 실제 데이터에서 덜 셌다 — DB `IN(...)`

**증상.** BOLA가 `distinct_where_ids=4`로 약하게 나옴(실제 18이어야).

**원인.** `WHERE user_id IN (4,5,...,18)`에서 **첫 숫자만** 매치하는 정규식이었다.

**해결.** `IN(...)` 괄호 전체를 잡아 안의 모든 숫자를 추출. 수정 후 18로 정상.

**교훈.** 정규식·파서는 **실제 데이터 형태로 검증**한다. `db_features.py --check`(파싱 커버리지·미파싱 샘플 출력)를 그래서 만들었다.

## #4 데이터셋이 측정하는 공격이 우리와 달랐다 — CSIC

**증상.** CSIC을 우리 **행위 피처**로 돌리니 Recall 0.15~0.24로 낮음.

**원인.** CSIC은 **요청 내용(페이로드) 공격**(SQLi·XSS)이고, 우리 피처는 **행위**(BOLA·느린공격·열거). 측정 대상이 다르다. 게다가 초기 변환기가 `err_ratio`·`interval_cv`를 상수로 내보내 피처가 빈약했다.

**해결.** `load_csic.py`를 **내용 피처**(sqli/xss/traversal 토큰·특수문자 비율·경로 길이)로 재설계.

**교훈.** 공개 데이터로 교차검증할 때 **그 데이터가 어떤 공격을 담는지** 먼저 확인한다. 내용 기반 ≠ 행위 기반. 우리 프로젝트는 행위 기반이므로 CSIC은 "파이프라인이 외부 데이터에서도 도나" 확인용이다.

## #5 모델이 느린 공격을 놓침 — (이건 함정이 아니라 설계로 이어진 발견)

**증상.** IsolationForest가 느린 BOLA 구간을 놓침(E2 탐지율 0.43).

**원인.** IF는 학습 때 본 값의 **범위 밖으로 외삽을 못 한다**. 느린 공격은 요청 수가 정상과 비슷해 전체적으로 안 튄다.

**해결.** 국소 밀도를 보는 **LOF**, 재구성 오차를 보는 **Autoencoder**를 추가 → 둘 다 느린 BOLA를 잡음. (학계·실무도 같은 결론, `docs/16` §0)

**교훈.** 모델의 **약점을 데이터로 드러내고**(leave-one-group-out), 그 약점을 보완하는 모델을 더한다. 한 모델에 의존하지 않는다.

---

## 이 로그를 왜 남기나

면접·발표·미래의 나에게 **"결과"보다 "판단"을 보여준다.** 좋은 숫자를 자랑하는 것보다,
"완벽한 점수를 의심해서 평가가 틀렸음을 찾아내 고쳤다"가 엔지니어의 실력이다.
새 함정을 만나면 같은 형식(증상→원인→해결→교훈)으로 여기에 계속 추가한다.
