## 2. 7주차 — 데이터 엔지니어링 파이프라인

### 2-1. 로그 파싱 고도화

- **alerts.json**: `detector/wazuh_ml_detect.py`의 파서를 import해 재사용 (정의가 두 벌이 되면 피처 값이 달라짐 — `05` §5-1)
- **archives.json**: 이벤트의 `full_log`에 nginx 접근 로그 원문이 들어 있다 → combined 형식 정규식으로 시각·IP·메서드·경로·상태·크기·User-Agent 추출
  - `location`(로그 파일 경로)으로 nginx / SSH(`/var/log/secure`) 이벤트를 구분
  - 같은 이벤트가 룰에 걸렸으면 alerts.json에도 있다 → 원문 해시로 연결해 "룰에 걸렸는가" 플래그를 단다
- 출력 통계: IP별 요청·알럿 수 상위 N / 룰별 건수·최고 레벨 / 시간대 분포 / **경로별 상태코드 분포**
- 주의: 시각은 **원래 이벤트 시각, UTC로 통일**

### 2-2. MySQL 스키마 (정규화 초안)

```sql
-- 차원
CREATE TABLE agent (
  agent_id    VARCHAR(16)  PRIMARY KEY,
  name        VARCHAR(64)  NOT NULL
);
CREATE TABLE rule (
  rule_id     INT          PRIMARY KEY,
  level       TINYINT      NOT NULL,
  description VARCHAR(255) NOT NULL
);
CREATE TABLE endpoint (
  endpoint_id INT AUTO_INCREMENT PRIMARY KEY,
  method      VARCHAR(8)   NOT NULL,
  path_tmpl   VARCHAR(255) NOT NULL,           -- 숫자 ID를 {id}로 치환한 경로 템플릿
  UNIQUE (method, path_tmpl)
);

-- 사실: 웹 요청 1건 = 1행 (archives.json의 nginx 줄)
CREATE TABLE web_request (
  req_pk      BIGINT AUTO_INCREMENT PRIMARY KEY,
  event_hash  BINARY(32)    NOT NULL UNIQUE,   -- SHA-256(full_log) → 재적재 중복 방지
  ts_utc      DATETIME(3)   NOT NULL,
  agent_id    VARCHAR(16)   NOT NULL,
  src_ip      VARBINARY(16) NOT NULL,          -- INET6_ATON()
  endpoint_id INT           NULL,
  raw_path    VARCHAR(1024) NOT NULL,          -- 공격자가 쓸 수 있는 값 → 데이터로만 취급
  object_id   VARCHAR(64)   NULL,              -- 경로 속 객체 ID (행위 층 피처용)
  status      SMALLINT      NOT NULL,
  bytes       INT           NULL,
  user_agent  VARCHAR(512)  NULL,
  rule_id     INT           NULL,              -- alerts.json에 같은 이벤트가 있으면 그 룰
  FOREIGN KEY (agent_id)    REFERENCES agent(agent_id),
  FOREIGN KEY (endpoint_id) REFERENCES endpoint(endpoint_id),
  FOREIGN KEY (rule_id)     REFERENCES rule(rule_id)
);

-- 사실: 알럿 1건 = 1행 (alerts.json — SSH 등 웹 외 알럿 포함)
CREATE TABLE alert (
  alert_pk    BIGINT AUTO_INCREMENT PRIMARY KEY,
  event_hash  BINARY(32)    NOT NULL UNIQUE,
  ts_utc      DATETIME(3)   NOT NULL,
  agent_id    VARCHAR(16)   NOT NULL,
  rule_id     INT           NOT NULL,
  src_ip      VARBINARY(16) NULL,
  FOREIGN KEY (agent_id) REFERENCES agent(agent_id),
  FOREIGN KEY (rule_id)  REFERENCES rule(rule_id)
);

-- 정답지 (05 §5-2 형식) · 탐지 결과
CREATE TABLE answer (
  attack_id   VARCHAR(16)   PRIMARY KEY,
  src_ip      VARBINARY(16) NOT NULL,
  start_utc   DATETIME      NOT NULL,
  end_utc     DATETIME      NOT NULL,
  type        VARCHAR(64)   NOT NULL,
  expected    VARCHAR(64)   NULL
);
CREATE TABLE detection (
  run_id       VARCHAR(32)   NOT NULL,         -- 모델+파라미터+실행 시각
  method       VARCHAR(16)   NOT NULL,         -- rule / zscore / iforest / lof / ocsvm / timeseries
  input        VARCHAR(16)   NOT NULL,         -- alerts / archives (09 Q12 비교)
  src_ip       VARBINARY(16) NOT NULL,
  window_start DATETIME      NOT NULL,
  score        DOUBLE        NULL,
  is_anomaly   TINYINT(1)    NOT NULL,
  PRIMARY KEY (run_id, src_ip, window_start)
);
```

설계 메모
- `rule.level`·`description`은 알럿마다 반복되므로 분리 (3NF). 적재 시 최신 값으로 UPSERT
- `web_request.rule_id`로 **같은 요청이 룰에 걸렸는지** 바로 알 수 있다 → "archives에만 있는 이상"(룰이 놓친 것) 집계가 쿼리 한 줄
- 행위 층 피처 표(IP × 5분)는 **뷰 또는 배치 테이블** — 분석용 비정규화는 의도된 선택
- 분석 단위 주체: **출발지 IP**를 기본으로 (`07` §5 "사용자(IP·토큰)"). 이유는 아래 "왜 nginx 로그엔 계정이 없나"

**왜 nginx 로그엔 계정이 없나**

```
브라우저 ──▶ [nginx: 전달 + 접근 로그 기록] ──▶ [Juice Shop 앱: 토큰 검사·사용자 인증]
```

- 같은 사이트지만 서버 안에선 프로그램이 둘이다. nginx는 요청을 전달하고 기록만 하며, **토큰을 검사하지 않는다.** 사용자 판별은 앱이 한다
- 토큰(JWT)은 접속 때가 아니라 **로그인 때** 앱이 발급하고, 이후 요청마다 `Authorization: Bearer <토큰>` 헤더로 실려 온다
- nginx 기본 형식(combined)은 IP·시각·요청줄·상태·크기·Referer·User-Agent만 적는다. `Authorization`은 기본 미기록 — 토큰은 그 자체로 로그인 상태라 로그에 남으면 탈취·재사용 위험이 있기 때문

| 방법 | 내용 | 판단 |
|---|---|---|
| **A. IP를 주체로** | 정상 사용자 스크립트를 사용자마다 다른 IP(컨테이너 등)로 실행 | **기본** — 설정 변경 없음 |
| B. 랩 한정 토큰 기록 | nginx `log_format`에 `$http_authorization` 추가 → 분석 스크립트가 토큰 안의 사용자 ID만 꺼내고 토큰은 버림 | 계정 단위 분석이 꼭 필요할 때만. **격리된 랩에서만, 공유 전 토큰 칸 삭제** |

### 2-3. 인덱스 + EXPLAIN (SQLP 연계)

| 쿼리 | 조건 / 그룹 | 인덱스 후보 |
|---|---|---|
| 시간별 건수 | `WHERE ts_utc BETWEEN ? AND ?` `GROUP BY` 시간 | `web_request(ts_utc)` |
| 행위 층 피처 | IP별 5분 구간 집계 | `web_request(src_ip, ts_utc)` |
| 룰이 놓친 요청 | `WHERE rule_id IS NULL AND ts_utc BETWEEN …` | `(ts_utc, rule_id)` |
| 룰별 집계 | `alert` 기간 + `GROUP BY rule_id` | `alert(ts_utc, rule_id)` → 커버링 |

실습 절차
1. 인덱스 없이 `EXPLAIN` / `EXPLAIN ANALYZE`(MySQL 8.0.18+) → `type=ALL`, `rows`, 실제 시간 기록
2. 인덱스 추가 후 같은 쿼리 → `type=range/ref`, `Using index`(커버링), 시간 비교
3. 반례: `WHERE DATE(ts_utc) = …`처럼 컬럼을 함수로 감싸면 인덱스를 못 탄다 → 범위 조건으로 다시 쓰기
4. 복합 인덱스 컬럼 순서(`(src_ip, ts_utc)` vs `(ts_utc, src_ip)`)를 바꿔 선두 컬럼 규칙 확인
5. 결과는 `pipeline/explain.md`에 전/후 실행계획 + 측정 시간 표로

⚠️ 수집 기간이 짧아 행 수가 적으면(수천 행) 옵티마이저가 풀스캔을 고르는 게 정상이다. 실행계획 실습은 **정상 사용자 스크립트를 길게 돌려 행 수를 늘린 뒤**(`08` §3 "길수록 좋음") 하거나, 적재된 **정상 요청 행만 복제**해 부피를 키워 진행한다 (부피 실습용 별도 DB, 탐지·채점에는 사용 금지).

### 2-4. Python → MySQL 자동 적재

- 드라이버: `PyMySQL`
- 차원 테이블 UPSERT(`INSERT … ON DUPLICATE KEY UPDATE`) → 사실 테이블은 `executemany` 배치 + `INSERT IGNORE`(event_hash UNIQUE)
- 증분: 파일별 마지막 오프셋을 `load_state` 테이블에 저장, `--watch`로 주기 실행. 파일 크기가 오프셋보다 작아지면(로테이션) 처음부터
- archives.json은 크다 → **nginx·SSH 이벤트만 골라** 적재 (`location` 필터). 실험 기간만 켜는 `08` §2-4 디스크 주의와 같은 이유
- 접속 정보는 환경변수(`MYSQL_HOST` 등), 커밋 금지

### 2-5. 통계 리포트 자동 생성

- `queries.sql`: 시간별 / 룰별 / IP별 / 경로별 상태코드 / **룰에 안 걸린 요청 비율**
- 수집 기간이 1~2일이면 "일별"은 점이 1~2개 → **시간별·5분별**을 기본으로
- 반복 리포트는 요약 테이블로 사전 집계
- 출력: `reports/` (Git 제외)

### 2-6. 환경 메모

- 개발 PC에는 MySQL·Docker가 없다 (2026-10-23 확인) → Wazuh 매니저 쪽 VM이나 별도 VM에 MySQL 설치, 또는 개발은 SQLite + EXPLAIN 실습만 MySQL
- ELK가 이미 있으므로 MySQL은 **정형 통계·SQL 실습용**, 시각화는 Kibana로 역할을 나눈다

## 3. 8주차 — ML 기반 이상 탐지 (행위 층)

단위: **IP × 5분 구간** (`07` §5 행위 층). 모든 모델은 같은 피처 표를 읽고 결과를 `detection`에 쓴다.

### 3-0. 피처 (`07` §5 행위 층 피처 기준)

| 피처 | 정의 | 보는 것 |
|---|---|---|
| `req_count` | 요청 수 | 양 |
| `uniq_objects` | 서로 다른 객체 ID 수 | 접근 범위 (BOLA 징후) |
| `err_ratio` | 4xx·5xx 비율 | 권한 오류·없는 경로 접근 |
| `interval_cv` | 요청 간격 표준편차 ÷ 평균 | 규칙성 (0에 가까울수록 기계적) |
| `browse_order_ratio` | 조회 대비 장바구니·주문 비율 | 조회만 하는 행동 (`07` B4) |
| `endpoint_entropy` | 호출 경로 분포 엔트로피 | 경로 다양성 (기존 엔트로피 코드 재사용, `06` §4) |
| `alert_count`, `rule_level_max` | 같은 구간의 Wazuh 알럿 | 룰과 결합 |

입력 비교(`09` Q12): **alerts.json만으로 만든 피처** vs **archives.json(전체)로 만든 피처** — 같은 모델에 넣어 차이를 본다.

### 3-1. 베이스라인 — Z-score

- **정상 수집 기간**(`08` §3, 공격 금지 기간)으로 피처별 μ·σ → 공격 기간 구간에 `z = (x − μ) / σ`, |z| ≥ 3이면 이상
- 한계
  - 보안 로그는 정규분포가 아니다(대부분 작고 가끔 폭증) → **중앙값·MAD 기반 robust Z**와 비교
  - 피처를 하나씩 본다 → "각각은 평범한데 조합이 이상한" 경우를 못 잡음 → 다변량 모델이 필요한 이유

### 3-2. 비지도 모델 — Isolation Forest · LOF · One-Class SVM

- 학습: **정상 수집 기간 피처로 fit** → 공격 기간 포함 전체에 점수 (`09` Q7·Q8: 정상 기준은 우리 랩 정상 로그)
- 같은 틀에서 세 모델 교체 (scikit-learn `IsolationForest`, `LocalOutlierFactor(novelty=True)`, `OneClassSVM`)
- LOF·OCSVM은 거리 기반이라 **피처 스케일링 필수**(StandardScaler, 정상 기간으로 fit). IF는 불필요
- 실험: 임계값(contamination·nu), 피처 제거(랩 01 실험 B와 동일), IP·시간대 피처 제거 시 탐지 유지 여부(`05` §1)

### 3-3. 시계열 — 이동평균/분산

- 5분·1시간 단위 요청 수·알럿 수 시계열, 이동평균 ± k·이동표준편차(k=2~3) 밴드 이탈 = 이상
- 볼 것: 느린 공격은 **전체 건수 시계열엔 묻히고** IP별 행위 피처에서 드러남 → 3-1·3-2와 상호 보완
- 수집이 1~2일이면 하루 주기 1~2회, 요일 주기 0회 관측 → **주기 학습은 하지 않고** 밴드까지만, 한계로 명시

### 3-4. 대시보드 — Kibana (기존 ELK)

- Wazuh 대시보드(OpenSearch 기반)와 Home SOC Lab의 ELK(Kibana)는 별개 → **우리 탐지 결과를 ELK에 보낸다**
- 방법: `detection` 행을 Elasticsearch 인덱스(예: `ml-detection-*`)로 bulk 전송 → Kibana에서 시간대별 요청 + 이상 구간, 모델별 이상 IP, 룰 vs ML 비교 패널
- ⚠️ Kibana의 **ML 이상탐지 작업(ML jobs)** 은 Elastic 유료 구독/체험판 기능 → 쓰려면 체험판 라이선스로 별도 비교 실험. 본 실험은 **우리 모델 결과의 시각화**로 충분

### 3-5. 탐지 성능 평가 — Precision / Recall / F1

- 정답: `answer` 테이블 (`08` §4 정답지 — 시각·출발지·공격 종류)
- 판정 단위: **IP × 5분 구간** — 정답지의 공격 시간대와 겹치는 해당 IP 구간 = 양성
- 정상 수집 기간이 있으므로 FP를 계산할 수 있다 (정상 구간에서 이상 판정 = FP)

  | 방식 | 입력 | TP | FP | FN | Precision | Recall | F1 | 느린 공격 | BOLA |

  | 룰 (레벨 10+) | alerts | | | | | | | | |
  | Z-score | archives | | | | | | | | |
  | Isolation Forest | alerts / archives | | | | | | | | |
  | LOF | archives | | | | | | | | |
  | One-Class SVM | archives | | | | | | | | |

- 공격 건수가 적으면 F1이 한두 건에 크게 흔들림 → 건수도 함께 표기
- 이 표가 `07` §6의 ①룰 vs ②ML 결과가 된다. ③LLM·④조합은 랩 01 `step4_llm.py` 구조로 이어서 (ML 상위 후보의 **숫자 요약**을 전달, 원문 전달 시 로그 조작 위험 고려)
