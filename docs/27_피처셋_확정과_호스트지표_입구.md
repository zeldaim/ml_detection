# 27. 피처셋 확정(v1) + node_exporter 호스트 지표 입구

> 플라이휠 1차를 마무리하며 **"무엇을 피처로 쓰나"를 데이터 근거와 함께 고정**하고,
> `docs/26` §4에서 미구현으로 남긴 **호스트 지표(node_exporter) → ML 입구**를 만든다.
> 기준 코드: `ml/feature_spec.py`(단일 출처), `ml/ablation.py`(소거 실험), `edge/host_metrics.py`(입구), `ml/per_key_eval.py`.
> 모델 측 요약: `models/MODEL_CARD.md`.

## 0. 결정 요약

| 셋 | 피처 수 | 상태 | 근거 |
|---|---|---|---|

- `train_export.py --feature-set web_v1` → 번들에 `feature_set` 이 기록되고, 그 열·그 순서만 학습한다.

## 1. 확정 규칙 (무엇을 남기나)

1. **빼 봐서 떨어지는가** — drop-one 소거, 비지도 3모델, **seed 10개 평균**(AE·IF 초기값 흔들림 ±0.04 를 피처 효과와 분리).
2. 노이즈를 넘게 탐지율↓ = **탐지**, 오탐↑ = **오탐억제**, 노이즈 내 = **중립**, 이 데이터에 해당 공격 없음 = **커버리지**.
3. 중립·커버리지도 **해가 없고 `docs/15` 공격 매핑상 맡은 클래스가 있으면 유지**. 단 다음 데이터에서 제거 1순위로 표시.
4. 분산 0(어떤 소스에서 늘 같은 값)은 제외 — 정보도 없고 검증도 불가.

## 2. web_v1 — 소거 실험 (실제 정본, `datasets/real_web/real_canon_*`)

분할: 정상 시간순 앞 70% 학습(149) / 뒤 30% 평가(65) + 공격 32구간(9종). contamination 0.05, seed 10개.
AE 은닉층은 모든 설정에서 5(전체 10피처 기준)로 고정 — 피처 수에 따라 용량이 바뀌면 피처 효과와 섞인다(리뷰 지적 반영).
재현: `docs/27 §6` 명령.

- **BOLA 신호(`uniq_objects`)가 전체 앙상블을 0.91→0.77로 끌어내린다** — 이 프로젝트의 중심 공격 클래스와 일치.
- **속도 축(`max_req_1min`)과 그 상대화(`rel_*` 묶음), 내용/규칙성 축(`interval_cv`·`endpoint_entropy` 묶음)이 각각 LOF를 0.81로 떨어뜨린다** = `docs/21` §J·K "축 분리"가 소거 실험에서도 재확인.
- IF는 `rel_*`를 빼면 오히려 오른다(0.32→0.43): 배수 피처는 꼬리가 길어 IF의 축 분할을 흐린다. **IF는 이 셋에서 앙상블 보조**(`MODEL_CARD` §4).

### 2-1. 이전 수치 정정 — "0.97"은 seed 하나의 값
`docs/21` §L·CHANGELOG 의 **IF|LOF|AE 0.97** 은 AE seed 0 한 번의 결과다. seed 10개 평균은 **0.91±0.04**.
차이 3구간(harvest_slow 3개)은 AE 초기값 운이다. 앞으로 AE가 들어간 수치는 seed 평균으로 낸다(`ml/ablation.py`).

## 3. node_exporter 입구 (`edge/host_metrics.py`)

### 3-1. 왜 따로인가 (`docs/26` §2)
호스트 지표는 **API 로직 공격(BOLA 등)엔 신호가 없다**. 대신 로그가 못 보는 **자원/가용성 공격**(채굴·연결 폭주·유출)을 본다.
뻔한 임계(CPU 100% 10분)는 Prometheus Alertmanager → SOAR 로 충분하고, ML 은 **미묘·다변량**(평소 대비 3배 송신 같은)을 맡는다.

### 3-2. 입력 3가지 → 같은 코드
```
Prometheus API (query_range) ──┐
저장된 query_range JSON(.gz) ──┼─▶ 원시 시계열 (host, series, ts, value)
/metrics 텍스트 스냅샷 ────────┘        │  카운터 → 차분/시간 = 초당 속도 (리셋=음수 차분은 버림)
  (Prometheus 없는 랩: --collect)        ▼
                               호스트 × 5분 구간 → host_v1 12피처 CSV (열 'ip' = 호스트)
                                         ▼
                 train_export / predict / relative_features / supervised 그대로 사용
```
- 원시 카운터를 받아 **속도 계산을 한 곳에서** 한다 → API 경로와 스냅샷 경로의 출력이 **바이트 단위로 같음**을 확인(같은 합성 데이터, `cmp` 일치).
- 가상 장치(`lo`·`veth`·`docker`·`loop`·`dm-`…)는 제외 — 생성기에 루프백 50MB/s·loop 디스크 80MB/s 를 넣어 걸러지는지 시험(걸러짐).
- 표본이 기대치(구간 ÷ 표본 간격)의 `--min-coverage`(50%) 미만인 구간은 버림(수집 끊김을 '조용함'으로 오인 방지).
- **step < scrape 간격 방어:** Prometheus 는 step 마다 마지막 값을 반복해 준다. CPU 카운터 합이 늘지 않은 시각(= 반복)을 먼저 버려,
  scrape 60초를 step 15초로 받아도 출력이 같다(시험: 같은 데이터를 4번씩 반복시켜 비교 → 동일). 이걸 안 하면 망·디스크 속도가 4배로 부풀었다(리뷰 HIGH).
- 그 밖에: 시간대 없는 `--start/--end` 는 UTC 로 해석, 긴 범위는 하루 단위로 나눠 요청(시계열당 11,000점 제한),
  CPU 지표가 없는 호스트는 경고 후 건너뜀, `steal` 은 busy 에서 제외(VM 이웃 소음), 본딩/브리지·md 는 이중 집계라 제외.

### 3-3. host_v1 피처
| 피처 | 계산 | 겨냥 |
|---|---|---|
| `cpu_busy_mean` | 1 − (idle+iowait)/전체 cpu초 | 채굴·DoS |
| `cpu_busy_sustain` | 구간 내 busy ≥ 0.8 표본 비율 | 채굴(지속) vs 배치(짧음) |
| `cpu_iowait_mean` | iowait/전체 | 디스크 대량 읽기 |
| `load1_per_cpu_max` | load1 / 코어 수 | 과부하 |
| `mem_used_ratio` | 1 − MemAvailable/MemTotal | 메모리 고갈 |
| `net_rx_Bps` · `net_tx_Bps` | 물리 NIC 합 초당 바이트 | DoS · 유출 |
| `tx_rx_ratio` | tx/(rx+1) | 유출(송신 편중) |
| `net_tx_cv` | 송신 속도 변동계수 | 버스트 유출 |
| `tcp_estab_max` | `node_netstat_Tcp_CurrEstab` 최대 | 연결 폭주 |
| `disk_io_Bps` | 읽기+쓰기 초당 바이트 | 백업(하드네거티브)·랜섬웨어 |
| `procs_running_max` | 실행 중 프로세스 최대 | 채굴·포크 |

### 3-4. 설계 결정: **호스트별 기준선 모델** (데이터 근거)
합성 3호스트 × 8시간, 공격 4종(채굴·연결폭주·버스트유출·느린유출) + 정상 하드네거티브(배치 CPU·백업 송신). `ml/per_key_eval.py`:

| | 통합 모델(호스트 섞음) | **호스트별 모델** |
|---|---|---|
| LOF 탐지 | 0.52 (13/25) | **1.00 (25/25)** |
| LOF 오탐 | 0.05 (4/81) | 0.05 (4/81) |
| `exfil_slow`(앱서버 송신 ×3) | **0/12** | **12/12** |
| IF\|LOF\|AE 오탐 | 0.07 | 0.15 (호스트당 학습 ~60구간이라 AE 불안정) |

- **이유:** 앱서버의 '평소 3배 송신'은 DB 서버의 평소 수준이다. 섞으면 한 호스트의 이상이 다른 호스트의 정상에 묻힌다.
  = 웹 UEBA(§K)의 "자기 대비" 원리를 **모델 단위**로 적용한 것.
- UEBA 배수(`rel_*`)를 통합 모델에 넣어도 0/12 그대로였다 — 백업 창의 배수(~30)가 스케일을 키워 3배가 묻힘. 그래서 host_v1 엔 `rel_*` 을 넣지 않았다.
- **권장: 호스트(또는 역할)별 LOF 단독.** 호스트별 AE 는 학습 표본이 쌓인 뒤 재평가.
- **계절성 요구사항:** 처음엔 합성 부하 주기를 8시간 전체에 1번 두었더니, 앞 70% 학습이 골짜기를 못 봐서 호스트별 오탐이 14~17/26 이었다.
  주기를 학습 구간 안에 들게(2시간) 하자 4/81(전 호스트 합). → **실제로는 학습 기간이 최소 한 주기(하루, 가능하면 주간)를 덮어야 한다.**

> ⚠ 전부 **합성**이다. 숫자는 "입구가 돌고 설계 판단이 데이터로 갈린다"의 확인이지 성능 증거가 아니다(합성 포화 교훈, `docs/21` §6).
> 특히 `exfil_burst` 와 정상 백업은 '송신 급증'이 같아 실제로는 **스케줄 allowlist(룰 영역)** 가 먼저다(`docs/26` §3).

### 3-5. 실측 절차 (랩 VM, 다음 바퀴)
> 인프라 배치(어디에 무엇을 설치하나)는 **`docs/28`**. 아래는 수집기 없이 빠르게 해 볼 때의 최소 절차.
```bash
# Rocky VM(10.16.1.10) — node_exporter 설치(단일 바이너리, :9100)
./node_exporter &                         # 또는 systemd 유닛
# 분석 PC — Prometheus 없이 스냅샷 수집(15초 × 24시간 이상: 계절성 1주기)
python edge/host_metrics.py --collect http://10.16.1.10:9100/metrics --out-dir data/host_snap --interval 15 --duration 86400
# 공격 러너가 attack_id,src,start,end,type 로 정답지 기록(채굴=stress-ng, 유출=대용량 scp, 폭주=hping3/ab)
python edge/host_metrics.py --snapshots data/host_snap --out data/host_features.csv
python ml/per_key_eval.py data/host_features.csv --answer data/host_answer.csv
python edge/host_metrics.py --snapshots data/host_snap --out data/host_features.csv --per-host-dir data/host_by_host
python ml/train_export.py data/host_by_host/10.16.1.10.csv --answer data/host_answer.csv --feature-set host_v1 --out models/host_10.16.1.10.joblib
```
Prometheus 가 이미 있으면 `--prom http://<prom>:9090 --start … --end …` 로 같은 결과(스크레이프 간격과 `--step` 을 맞출 것).

## 4. 이번에 발견한 결함 (그리고 고친 것)

> 아래 v3 결함 외에, 이 문서의 코드는 **독립 코드 리뷰**(작성과 분리된 검토)를 거쳐 14건을 반영했다:
> 호스트 입구 속도 부풀림(HIGH, §3-2), `per_key_eval` 의 공격 전용 키 처리, 소거 실험의 AE 용량 혼입(§2),
> `train_export` 의 부분 불일치 경고·`--drop` 충돌·`type=normal` 정답 처리, verify.sh 이전 산출물 재사용 방지 등.

**`train_export.py` 가 IP형 정답지를 무시했다.** 라벨 조건이 `src == ip and start and …` 라서 `start` 가 없는 IP형(정본 정답지)은 매칭 0건
→ **공격 32구간까지 '정상'으로 학습**. 이전 "현재 최선" `model_web_v3_canon_rel.joblib` 의 `n_normal=246`(= 전체 행)이 그 흔적.

| 같은 정본에서 판정(in-sample) | IF | LOF | AE | IF\|LOF\|AE |
|---|---|---|---|---|
| v3 (공격 섞여 학습) | 11/32 | **8/32** | 11/32 | 19/32 |
| **v3.1 (정상 214만)** | 12/32 | **28/32** | 31/32 | **31/32** |

- 수정: `supervised.label_windows` 를 공유(두 정답지 형식 모두 처리) + **정답지가 한 구간도 못 맞추면 학습 중단**(조용한 실패 방지).
- 교차검증 수치(`supervised.py`)는 처음부터 이 함수를 썼으므로 **`docs/21` 실험 결과 자체는 유효**. 영향은 저장된 배포 번들뿐.
- v3 번들은 지우지 않고 `models/archive/model_web_v3_canon_rel_trained-with-attacks.joblib` 로 보존(재현·비교용).

## 5. db_v1 — 합성 DB 아크 소거 (참고)
`datasets/real_db/db_arc_*`(정상 72, 공격 24구간 3종). 앙상블 1.00 이지만 **오탐 0.31** — 하드네거티브(리포트·빠른 합법)가 정상 쪽에 넓게 퍼짐.
탐지: `q_count`(빼면 0.77)·`sqli_token_hits`(0.77)·`distinct_where_ids`(LOF 0.67→0.33). 오탐억제: `select/write_ratio`·`distinct_tables`. 중립: `uniq_templates`·`interval_cv`.
→ **DB 는 운영급 아님.** 열만 db_v1 로 고정하고, 실제 MySQL(`docs/14`) 후 `docs/22` 파생 '반복도'(q_count/uniq_templates) 포함 여부를 v2에서 결정.
