# 29. 로그 수집·저장 — 결정 근거와 비교 (저장된 로그 투입 + 실시간 수집)

> 작성 2026-10-25. **"다른 인프라·다른 호스트의 로그를 ML 에 어떻게 넣나"** 에 대한 결정 기록.
> 두 경로를 둔다 — ① 이미 받은 파일을 넣는 **투입구**(`ml/ingest.py`, `inbox/README.md`), ② VM·원격 Wazuh 에서 계속 받는 **실시간 수집**(`deploy/collect/`).
> 관련: `docs/28`(랩 배치), `docs/26`(신호별 결정 로직), `docs/08` §2-4(alerts vs archives), `edge/README.md`(원문은 호스트 밖으로 안 나감).

## 0. 결정 요약

| 질문 | 결정 | 한 줄 근거 |
|---|---|---|
| 받은 로그 파일을 ML 에 넣는 법 | **`inbox/<이름>/` 에 넣고 `python ml/ingest.py inbox/<이름> [--retrain]`** | 파일 종류를 내용으로 알아보고, 기존 스크립트를 순서대로 불러 **돌린 명령을 보고서에 남김**(흐름이 보이게) |
| VM·원격 로그를 계속 받는 법 | **ML PC 에 Logstash 수신기** → `inbox/live/<출처>/<로그종류>/` 에 원문 그대로 파일로 | "ML PC 폴더에 바로 쌓인다" — 투입구와 같은 폴더 구조라 그대로 `ingest.py` |
| 보내는 쪽(랩 VM) | **Filebeat** | Logstash 와 짝(Beats 프로토콜), 위치 기억·재전송 |
| 보내는 쪽(원격 Wazuh manager) | **Fluent Bit** 가 `archives.json` 을 읽어 복사본 전송 | 그쪽 Wazuh·SIEM 을 건드리지 않음. Wazuh 가 이미 쓰는 Filebeat 와 충돌 없음 |
| 전송 보안 | **상호 TLS**(우리 CA 가 서명한 인증서를 가진 쪽만 접속) + 외부는 VPN | 수신 포트가 ML PC 에 열림 → 아무나 로그를 밀어 넣지 못하게 |
| DB 쿼리 원문 | **어느 경로로도 안 보냄.** DB VM 안에서 `db_features.py` → 피처 CSV 만 | 쿼리 = 개인정보. `edge/` 원칙 |
| API Gateway 를 앞에 두면 | **게이트웨이 access log 를 ML 주 입력으로 수집.** 뒤쪽 nginx 는 `real_ip` 로 원래 IP 복원(교차 확인·WAF용) | 게이트웨이 = 리버스 프록시 → 뒤쪽엔 게이트웨이 IP 하나만 찍힘. 클라이언트를 직접 보는 **첫 L7 지점**에서 기록 (§7) |

## 1. 두 경로는 무엇이 다른가

```
① 저장된 로그 (배치)                         ② 실시간 수집 (스트림)
 받은 파일(USB·메일·scp·버킷 다운로드)          VM/원격 Wazuh ─ Filebeat/Fluent Bit ─TLS─▶ ML PC Logstash
        │ 사람이 복사                                                                │ 자동으로 파일에 씀
        ▼                                                                            ▼
 inbox/<이름>/                                   inbox/live/<출처>/<로그종류>/<호스트>-<날짜>.log
        └──────────────── 둘 다 ────────────────────────┘
                  python ml/ingest.py <폴더> [--retrain]   → <폴더>/out/REPORT.md
```
**ML 쪽 코드는 하나다.** 로그가 어떻게 도착했든 폴더에 파일로 있으면 같은 `ingest.py` 가 처리한다. 수집 방식을 바꿔도 ML 은 안 바뀐다 — 이게 이 설계의 핵심.

## 2. 비교한 선택지 (실시간 수집)

### 2-1. 수신·저장 방식

| 방식 | 로그가 쌓이는 곳 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| **Logstash 수신 → 파일** | ML PC 폴더에 바로 | 폴더에 바로 쌓여 흐름이 단순 · 수신 단계에서 필터·정리 가능 · 팀의 ELK 경험(`docs/08`) | JVM 이라 메모리 ~1GB(힙 512MB 로 축소 가능) | ✅ **채택** |
| Fluent Bit 수신 → 파일 | ML PC 폴더에 바로 | 구조 같고 수십 MB 로 가벼움 | 팀에 익숙한 도구 아님 | 대안(메모리 빠듯하면 교체) |
| MinIO 버킷(S3) | 버킷 → 필요할 때 내려받기 | 원본 보관·수명주기 · 나중에 클라우드 S3 로 그대로 | 한 단계 더(내려받기) · 구성요소 하나 추가 | 보류(장기 보관이 필요해지면) |
| ML PC 에 Wazuh manager 추가 | — | — | **Windows 에 manager 없음**(Linux 전용) · **에이전트는 manager 하나에만 보냄** → 원격 에이전트를 우리 쪽으로 돌리면 그쪽 SIEM 이 로그를 잃음 · 랩엔 이미 Wazuh VM | ❌ |
| cron + rsync/scp | 복사한 폴더 | 가장 단순 | 재시도·이어읽기·보관을 직접 관리 · SSH 계정 필요 | 원격 대안(§2-2) |

### 2-2. 원격 Wazuh 의 로그를 받는 법

> **먼저 확인:** Wazuh 는 기본으로 **룰에 걸린 경보(`alerts.json`)만** 저장한다. 전체(`archives.json`)는 `logall_json` 을 켜야 남는다.
> 우리 ML 은 "룰이 놓친 것"을 찾으므로 **경보만 받으면 쓸모가 거의 없다**(`docs/08` §2-4) → 어떤 방법이든 첫 요청은 "`logall_json` 켜 주세요".

| 방법 | 그쪽에 필요한 것 | 장점 | 한계 | 판정 |
|---|---|---|---|---|
| **manager 에 Fluent Bit → 우리 Logstash** | 작은 에이전트 + 우리가 준 클라이언트 인증서 | 그쪽이 **보내는(push)** 방식 → SSH 불필요 · 준실시간 · 그쪽 SIEM 무변경 | 설치 허락 필요 | ✅ **기본** |
| SSH 로 `archives.json` 주기 복사 | 읽기 전용 SSH 계정 | 단순, 받은 파일은 바로 `inbox/` | 계정 받기 어려움 · 주기적 | 대안 ① |
| Wazuh 인덱서(OpenSearch) 검색 API | 읽기 전용 인덱서 계정 · 9200 접근 | 그쪽 설치 없음 | 인덱서엔 기본으로 **경보만** — 전체를 인덱싱하려면 그쪽 저장 부담 큼 | 대안 ② |
| Wazuh `syslog_output` | 설정만 | — | **경보만** 보냄 | ❌ |
| Wazuh API(55000) | — | — | 관리용 API, **로그를 꺼내는 기능 없음** | ❌ |
| 그쪽 에이전트를 우리 manager 로 | — | — | 그쪽 SIEM 이 로그를 잃음 | ❌ |

### 2-3. 보내는 쪽 에이전트

| | 랩 VM | 원격 Wazuh manager |
|---|---|---|
| 선택 | **Filebeat** | **Fluent Bit** |
| 이유 | Logstash Beats 입력과 짝 · 위치 기억(registry)으로 재시작 후 이어 보냄 | 그 서버엔 Wazuh 가 쓰는 Filebeat 가 이미 있음 → 하나 더 깔면 설정·서비스 충돌. Fluent Bit 는 별개 프로세스 |
| 버퍼 | ML PC 가 꺼져도 재시도 | 디스크 버퍼(`storage.path`)로 쌓았다 재전송 |

## 3. 저장 구조 (왜 이렇게 나눴나)

```
inbox/live/
 ├ lab/                       ← 출처(누가 보냈나) — 출처마다 '평소'가 다르니 섞지 않는다
 │  ├ nginx_shopapi/          ← 로그 종류(앱) — 앱마다 소유 자원 경로(owned_paths)가 다르다
 │  │  ├ web01-2026-11-01.log ← 보낸 호스트 - 수신 날짜(UTC)
 │  │  └ meta.json            ← (직접 둠) {"owned_paths": ["/api/orders/{id}", …]}
 │  └ nginx_juiceshop/
 └ team_b/
    └ wazuh_archives/
       └ wazuh-teamb-2026-11-01.log
```
- **출처·앱별 폴더 = `ingest.py` 를 돌리는 단위.** `ingest.py` 는 한 폴더에 nginx 와 archives 가 같이 있으면 같은 요청을 두 번 세지 않으려 nginx 만 쓴다 → 다른 출처가 섞이면 한쪽이 빠진다. 그래서 출처를 나눈다.
- **원문 한 줄 그대로 저장.** Logstash 에서 파싱하지 않는다 — 피처를 바꿔도 원문으로 다시 뽑을 수 있게(`edge_agent` 처럼 피처만 보내면 원본이 없어 재추출 불가).
- **파일명 날짜는 수신 시각**, 구간 계산은 원문 안의 시각으로(`ml/features.py`). 늦게 도착한 줄도 올바른 5분 구간에 들어간다.
- 보내는 쪽이 정한 이름(출처·종류·호스트)이 경로가 되므로, Logstash 가 **허용 문자만 남기고 `..` 를 막는다**(경로 조작 방지). 이름이 없으면 `_unlabeled/` 로 모아 눈에 띄게.

## 4. 구축 절차

### 4-1. 인증서 (ML PC, Git Bash)
```bash
bash deploy/collect/make_certs.sh server 10.16.1.1 <VPN 주소>    # ML PC 서버 인증서 (처음 한 번)
bash deploy/collect/make_certs.sh client web01                   # 보내는 쪽마다
bash deploy/collect/make_certs.sh client wazuh-teamb
```
- 보내는 쪽엔 **`ca.crt` + `<이름>.crt` + `<이름>.key` 3개만** 준다. `ca.key` 는 ML PC 밖으로 안 나감. `certs/` 는 `.gitignore`.
- 검증함(2026-10-25, 로컬): 이 스크립트로 만든 인증서로 **클라이언트 인증서가 있는 쪽만 연결되고, 없는 쪽은 서버가 거부**(`PEER_DID_NOT_RETURN_A_CERTIFICATE`).
  처음엔 Windows openssl 이 `<(...)` 를 못 읽어 조용히 실패했고, 확장 필드가 빠져 엄격한 검증기가 거부했다 → 둘 다 수정.

### 4-2. ML PC — Logstash
```powershell
# 1) logstash-<버전>-windows-x86_64.zip 을 C:\logstash 에 (JDK 내장). 버전 기록.
# 2) 메모리: C:\logstash\config\jvm.options 의 -Xms/-Xmx 를 512m 로
# 3) 설정 검사 → 실행
C:\logstash\bin\logstash.bat -f D:\ml_detection\deploy\collect\logstash\ml-ingest.conf --config.test_and_exit
C:\logstash\bin\logstash.bat -f D:\ml_detection\deploy\collect\logstash\ml-ingest.conf
# 4) 방화벽: 5044 는 랩 대역만, 5045 는 VPN 대역만
New-NetFirewallRule -DisplayName "ml-collect beats" -Direction Inbound -Protocol TCP -LocalPort 5044 -RemoteAddress 10.16.1.0/24 -Action Allow
New-NetFirewallRule -DisplayName "ml-collect tcp"   -Direction Inbound -Protocol TCP -LocalPort 5045 -RemoteAddress <VPN 대역> -Action Allow
```

### 4-3. 랩 VM — Filebeat
```bash
rpm --import https://artifacts.elastic.co/GPG-KEY-elasticsearch
dnf -y install https://artifacts.elastic.co/downloads/beats/filebeat/filebeat-<Logstash 와 같은 버전>-x86_64.rpm
cp deploy/collect/filebeat/filebeat-lab-web.yml /etc/filebeat/filebeat.yml
mkdir -p /etc/filebeat/certs && cp ca.crt web01.crt web01.key /etc/filebeat/certs/ && chmod 600 /etc/filebeat/certs/web01.key
filebeat test config && filebeat test output && systemctl enable --now filebeat
```
- 같은 VM 의 Wazuh 에이전트도 nginx 로그를 읽는다 — 서로 독립(파일을 읽기만 함).

### 4-4. 원격 Wazuh manager — Fluent Bit (상대 팀이 설치)
- 설정: `deploy/collect/fluent-bit/wazuh-archives.conf` 의 `source`·`src_host`·`host` 만 바꿔서 전달.
- 전제: `logall_json` 켜짐. 과거분은 `read_from_head false` 라 안 옴 → 필요하면 합의해서 파일로 받아 `inbox/` 에.
- **인터넷 너머면 ML PC 포트를 공개하지 말고 VPN(WireGuard/Tailscale)** 으로 연결하고 `host` 는 VPN 주소. 가정용 공유기 포트포워딩 금지.

### 4-5. 확인
```
[ ] Logstash 가 5044/5045 수신 중 (netstat -an | findstr 504)
[ ] inbox/live/lab/nginx_shopapi/web01-<오늘>.log 에 줄이 늘어남
[ ] 인증서 없는 접속이 거부됨: openssl s_client -connect 10.16.1.1:5044 (클라이언트 인증서 없이) → 실패해야 정상
[ ] _unlabeled/ 폴더가 비어 있음 (생기면 보내는 쪽 fields 설정 누락)
[ ] python ml/ingest.py inbox/live/lab/nginx_shopapi --retrain → REPORT.md 생성
```

## 5. 보안·운영 규칙
- **받은 로그 = 민감정보**(상대 사용자 IP·경로). `inbox/` 는 git 제외(README 만 커밋). 메신저·클라우드 드라이브로 옮기지 않는다.
- **보관 기간을 상대와 합의**하고 지운다. 예: 30일 지난 파일 삭제(작업 스케줄러)
  `forfiles /p D:\ml_detection\inbox\live /s /m *.log /d -30 /c "cmd /c del @path"`
- 인증서는 보내는 쪽마다 따로 → 한 곳이 유출되면 그 인증서만 폐기(재발급하고 CA 는 유지).
- DB 쿼리 원문은 수집하지 않는다. DB 피처는 실험 단위로 DB VM 에서 `db_features.py` 를 돌려 CSV 만 `inbox/` 에.

## 7. API Gateway 를 앞에 둘 때 — 원래 IP 보존과 수집 위치

> 작성 2026-10-26. API 보안을 위해 API Gateway(Kong·nginx 기반 게이트웨이·클라우드 API GW 등)를 앞에 두자는 의견에 대한 정리.
> 관련: `docs/25`(식별자·출발지 귀속 — FortiGate SNAT 도 같은 종류의 문제), `docs/31`(WAF), `docs/28` §4-3(shopapi `log_format`).

### 7-1. 문제 — 게이트웨이는 프록시다
```
클라이언트 1.2.3.4 ──▶ API Gateway 10.16.1.5 ──▶ nginx/shopapi 10.16.1.10
                                                  └ access log 첫 칸($remote_addr) = 10.16.1.5  (모든 요청)
```
- `ml/features.py` 의 `NGINX_RE` 는 **로그 한 줄의 첫 칸 IP 를 출발지**로 쓴다. 뒤쪽 로그를 그대로 수집하면 모든 사용자가 **출발지 하나**로 합쳐진다
  → "출발지 × 5분" 피처(`req_count`·`uniq_objects`·`interval_cv`…)가 거대한 한 덩어리가 되어 공격자/정상 구분 불가. **에러 없이 틀린 결과**
- ModSecurity·Wazuh 룰·차단 기록(`--block-file`)의 `srcip` 도 전부 게이트웨이 IP 가 된다. 이걸로 차단하면 **게이트웨이 = 전체 서비스**를 끊는다
- 우리 랩도 이미 같은 구조다: nginx 가 Juice Shop(`127.0.0.1:3000`) 앞 프록시라 Juice Shop 자체 로그엔 127.0.0.1 만 남는다 → 그래서 **nginx 에서** 수집한다

### 7-2. 결정 — 어디서 수집하나

| 선택지 | 출발지 IP | 사용자 id | 판정 |
|---|---|---|---|
| **게이트웨이 access log** | 클라이언트와 직접 연결 → **진짜 IP** | 게이트웨이가 인증(토큰 검증)하면 토큰의 사용자(`sub`)를 기록 가능 | ✅ **ML 주 입력** |
| 뒤쪽 nginx + `real_ip` 복원 | 헤더로 받은 IP(설정이 맞을 때만) | 앱 응답 헤더 `X-User-Id`(`docs/28` §4-3) | 보조 — 게이트웨이 로그와 **교차 확인**, ModSecurity 가 올바른 IP 를 쓰게 |
| 뒤쪽 nginx 그대로 | ❌ 게이트웨이 IP 하나 | — | ❌ ML 에 쓰면 안 됨 |

- 원칙: **클라이언트를 직접 보는 첫 번째 L7 지점에서 기록한다.** FortiGate(L3/L4)는 이 앞에 있어도 HTTP 경로를 못 보므로 해당 없음(SNAT 를 하면 게이트웨이마저 FortiGate IP 를 보게 되니 `docs/25` 확인)
- **두 로그를 같은 `ingest.py` 폴더에 넣지 않는다.** 같은 요청이 두 번 세진다. 출처·종류 폴더를 나눈다(§3): 예 `inbox/live/lab/gw_shopapi/` 와 `inbox/live/lab/nginx_shopapi/`
- **게이트웨이를 넣으면 "평소"가 바뀐다** — 로그 출처·필드·rate limit 이 달라지므로 재학습(`--retrain`), 실험 메타에 게이트웨이 종류·버전 기록 (WAF 와 같은 규칙, `docs/31` §6)

### 7-3. 게이트웨이 로그 형식 — `features.py` 가 읽을 수 있게
- **nginx combined 와 같은 칸 순서**로 남긴다: `IP 사용자id [시각] "메서드 경로 프로토콜" 상태 크기 "Referer" "UA"`. 2번째 칸은 사용자 id(없으면 `-`) — shopapi 로그와 같은 모양
- 게이트웨이가 JSON 로그만 낸다면(Kong 등) Logstash 에서 이 형식으로 한 줄 바꿔 쓰거나, `features.py` 에 파서를 추가한다(그때 `verify.sh` 회귀 검사 추가)
- 첫 칸은 반드시 **클라이언트 IP**. 게이트웨이 앞에 또 프록시/로드밸런서가 있으면 그 단계에서도 §7-4 를 적용
- 토큰 원문(`Authorization`)은 기록하지 않는다 — 사용자 id 만 (`docs/10` 방안 B 와 같은 원칙)

### 7-4. 뒤쪽에서 원래 IP 복원 — 헤더는 신뢰한 곳에서 온 것만
```nginx
# 게이트웨이 쪽: 원래 IP 를 헤더로 넘김 (nginx 기반이면)
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Real-IP       $remote_addr;

# 뒤쪽 nginx(웹 VM) http 블록: ngx_http_realip_module
set_real_ip_from  10.16.1.5;          # 게이트웨이 IP 만 신뢰 (대역 전체·0.0.0.0/0 금지)
real_ip_header    X-Forwarded-For;
real_ip_recursive on;                 # 오른쪽부터 신뢰 목록에 없는 첫 주소 = 실제 클라이언트 (프록시 여러 단계 대비)
```
- 이러면 `$remote_addr` 자체가 1.2.3.4 로 바뀌어 **access log 첫 칸·ModSecurity·Wazuh 가 모두 원래 IP** 를 쓴다 (`log_format` 수정 불필요)
- **`X-Forwarded-For` 는 클라이언트가 위조할 수 있다.** 공격자가 `X-Forwarded-For: 8.8.8.8` 을 붙여 보내도, 게이트웨이는 그 뒤에 진짜 IP 를 덧붙이고 뒤쪽은 신뢰 목록 밖의 가장 오른쪽을 고르므로 진짜 IP 가 나온다. **위조가 통하는 경우:** `set_real_ip_from` 을 넓게 잡아 클라이언트까지 신뢰하거나, 게이트웨이가 받은 헤더를 그대로 넘길 때(`proxy_set_header X-Forwarded-For $http_x_forwarded_for`). 그러면 위조 값이 출발지가 되어 탐지를 피하고, 차단 기록이 엉뚱한 IP 를 가리킨다. `real_ip_recursive` 는 신뢰하는 프록시가 **여러 단계**(예: 로드밸런서 → 게이트웨이)일 때 필요하다 — 그때는 두 IP 모두 `set_real_ip_from` 에
- 뒤쪽 서버는 **게이트웨이에서 온 연결만 받게** 막는다(FortiGate 정책 또는 웹 VM firewalld: 80/8080 은 게이트웨이 IP 만). 게이트웨이를 우회해 직접 들어오면 헤더 위조가 그대로 통한다

### 7-5. 게이트웨이가 해결하는 것 / 못 하는 것 (API 보안 관점)

| 게이트웨이 기능 | BOLA·API 공격에 대해 |
|---|---|
| 인증·사용자 식별 | 도움 — 누가 요청했는지 확실. ML 키를 IP 대신 사용자 id 로 쓸 수 있음(NAT 뒤 여러 사용자, IP 바꾸는 공격자에 강함) |
| Rate limit(사용자/IP당) | 일부 — 빠른 id 순회(열거)는 막힘. **느린 BOLA 는 못 막음** → ML(`boost_bola_slow`, `docs/30` §3) |
| 스키마 검증·허용 경로만 통과 | 인젝션·이상 파라미터 일부 차단 (내용 검사는 WAF, `docs/31`) |
| **"이 주문이 이 사용자 것인가"** | **못 함.** 객체 소유는 앱·DB 만 앎 → 앱의 소유권 검사가 근본 해결 |

### 7-6. 도입 때 확인
```
[ ] 게이트웨이 access log 첫 칸 = 접속한 PC 의 IP (게이트웨이 IP 아님)
[ ] 뒤쪽 nginx access log 첫 칸도 같은 IP (real_ip 동작)
[ ] 위조 시험: curl -H 'X-Forwarded-For: 8.8.8.8' … → 두 로그 모두 8.8.8.8 이 아니라 진짜 IP
[ ] 게이트웨이를 거치지 않고 웹 VM 80/8080 직접 접속 → 차단됨
[ ] 게이트웨이 로그를 ingest.py 에 넣어 출발지 수가 실제 접속 PC 수와 맞음 (1개면 실패)
[ ] Filebeat 가 게이트웨이 로그를 별도 종류(gw_*)로 보냄, 뒤쪽 nginx 로그와 폴더가 섞이지 않음
```
