# 34. 공공 클릭스트림으로 정상 행동 재현 — 데이터셋 후보와 Juice Shop 매핑

> 날짜: 2026-11-12 · 관련: `docs/33` §5-1(처음 보는 정상 출발지 오탐 평균 12%), `tools/gen_normal_traffic.py`(현재 정상 생성기)
> 상태: OTTO 원본 수령·샘플 커밋 완료(§3). 재생기 코드는 아직 없음.

## 0. 왜

`docs/33` §5-1: 출발지 단위로 나누면 LOF 정상 오탐이 평균 12%(시드별 0~18%). 학습에 없던 **종류의 정상 사용자**를 이상으로 본다.
real_canon 의 정상 출발지는 전부 `gen_normal_traffic.py` 가 만든 것이고, 행동의 '모양'이 생성기 코드로 정해져 있다:

| 생성기에 하드코딩된 것 | 값 | 문제 |
|---|---|---|
| 클릭 간격 | lognormal(2.0, 0.8), 2~45초로 자름 | 사람의 실제 간격 분포(수 초~수십 분 꼬리)와 다를 수 있음 |
| 세션 길이 | 행동 3~15회 균등 | 실제는 1회 이탈이 많고 꼬리가 긺 |
| 행동 비율 | 로그인 시 장바구니 30% · 리뷰 3% · 상품 32% · 검색 35% | 실제 전환 깔때기(조회 ≫ 장바구니 ≫ 구매)와 다름 |
| 다음 방문까지 | 1~15분 균등 | |
| 소유 자원 | 장바구니 1개만, 주소·카드·주문 없음 | `uniq_objects` 가 정상에서 거의 0 (214구간 중 198, `docs/33` §3) |

## 1. 아이디어 수정: 피처 값이 아니라 **행동 순서**를 옮긴다

처음 아이디어("공공데이터에서 정상 피처 값을 함수로 뽑아 대입")는 그대로는 안 된다:

1. **사이트에 따라 달라지는 피처는 못 옮긴다**: `uniq_objects`·`uniq_paths`·`endpoint_entropy`·`err_ratio` 는 사이트 경로 수·소유 자원 구조가 정한다.
   옮길 수 있는 건 사람의 시간 패턴(간격·세션 길이·재방문) 정도.
2. **피처를 하나씩 뽑으면 피처 간 관계가 깨진다**: LOF·IF 는 피처 조합을 본다. 따로 뽑은 정상 = 현실에 없는 조합 = 가짜 정상 학습.
3. **결국 또 생성기**: 팀원 실패 원인이 '생성기 정상 → 지름길'이었다.

→ 공공 데이터의 **세션(이벤트 순서 + 실제 시간 간격)** 을 가져와 이벤트를 **역할별로 우리 사이트 요청에 매핑**하고,
우리 사이트에 **재생**해서 기존 `features.py` 로 피처를 뽑는다.
시간 패턴·깔때기는 실제 사람에서, 사이트 구조·피처 간 관계는 우리 것에서 온다.

### 3-1. 샘플에서 확인한 것 — 생성기와 실제 사람의 차이

`ts` 는 **밀리초**(13자리, 전 세션). OTTO 의 `session` 은 한 번 방문이 아니라 **4주에 걸친 한 사용자 기록**에 가깝다
(세션 길이 중앙값 2.3일, 이벤트 간격의 16%가 30분 초과) → 30분 무활동으로 '방문'을 나눠 봤다.

| | OTTO (실제) | `gen_normal_traffic.py` |
|---|---|---|
| 방문 안 행동 간격 p10 / p50 / p90 | **7.6 / 37.8 / 202 초** | 2.7 / 7.4 / 20.5 초 (lognormal(2,0.8), 2~45초 자름) |
| 방문당 행동 수 p50 / p90 | 2 / 11 | 3~15 균등 (중앙 9) |
| 행동 1개로 끝나는 방문 | **39%** | 0% (최소 3) |
| 사용자당 방문 수 p50 / p90 | 2 / 7 (4주) | 생성 시간 동안 계속(1~15분 쉬고 재방문) |
| 깔때기 click : cart : order | 100 : 8.8 : 2.7 | 로그인 시 장바구니 30% |

→ 생성기 정상은 실제 사람보다 **약 5배 빠르게** 클릭하고, 바로 나가는 방문이 없다. `interval_cv`·`req_count`·`max_req_1min` 에 직접 영향.
(주의: OTTO 간격은 상품 이벤트 사이 간격이라 그 사이의 페이지·정적 요청은 우리 사이트 쪽에서 붙는다.)

## 4. 매핑: OTTO 이벤트 → Juice Shop 요청

real_canon 정상 로그에서 확인한 Juice Shop 경로 기준. 브라우저(SPA)가 실제로 내는 요청 묶음으로 바꾼다.

| OTTO / 상황 | Juice Shop 요청 (순서대로) | 비고 |
|---|---|---|
| 세션 시작 (첫 이벤트 전) | `GET /` → 정적(js·css) → `GET /rest/admin/application-version` · `/rest/admin/application-configuration` · `/rest/languages` · `/api/Quantitys/` → `GET /rest/products/search?q=` | 생성기 `page_load()` 와 같음. 정적 파일은 피처에서 빠지지만 간격 계산엔 영향 없음 |
| `click` (상품 조회) | `GET /rest/products/{pid}/reviews` | Juice Shop 상품 상세는 대화상자 → 리뷰 API 가 상세 조회의 흔적 |
| 첫 `cart` 직전 (로그인 안 된 상태) | `POST /rest/user/login` → `GET /rest/user/whoami` → `GET /rest/basket/{bid}` | 실제 사이트도 장바구니에 로그인 필요. 로그인을 장바구니 직전으로 미루면 '로그인만 하고 둘러보기' 비율은 Coveo 로 보정 |
| `cart` (새 상품) | `POST /api/BasketItems` → `GET /rest/basket/{bid}` | |
| `cart` (이미 담은 상품) | `PUT /api/BasketItems/{itemId}` (수량+1) → `GET /rest/basket/{bid}` | |
| `order` | `GET /api/Addresss` → `GET /api/Cards` → `POST /rest/basket/{bid}/checkout` → `GET /rest/basket/{bid}` | **소유 자원(주소·카드·주문)** 이 정상에도 생긴다 → `uniq_objects` 현실화. 사용자 계정에 주소·카드를 미리 만들어 둠 |
| 같은 상품 연속 click | 요청 1회로 합침 | 상세를 다시 여는 게 아니라 같은 페이지 체류 |
| 이벤트 간 간격 | OTTO `ts` 차이 그대로 (상한 30분 → 넘으면 새 세션) | 시간 패턴의 원천. 생성기 lognormal 을 대체 |

**상품 ID 매핑**: OTTO `aid`(180만 종) → Juice Shop 상품(~40개). `pid = 상품목록[hash(aid) % N]` — 같은 aid 는 항상 같은 상품이라
**재방문·반복 조회 패턴이 유지**된다. 대신 서로 다른 상품 수가 40개에서 포화 — 많이 본 세션의 `uniq_paths` 가 실제보다 작게 나온다(한계로 명시).

**출발지 매핑**: OTTO `session` 하나가 이미 여러 방문(중앙값 2회, 4주)을 담은 한 사용자 기록이므로(§3-1) **OTTO 세션 1개 = 정상 출발지 1개**.
30분 넘는 간격은 방문 사이 휴식으로 두고, 재생 시간을 줄이려면 방문 사이 간격만 압축(방문 안 간격은 그대로)한다.

**OTTO 에 없어서 우리 규칙으로 채우는 것** (= 여전히 생성기 부분, 결과 해석 때 구분)
- 검색 (`/rest/products/search?q=…`): OTTO 에 없음 → Coveo 검색 비율로 click 사이에 삽입
- 오류(4xx): 실제 사용자도 낸다(잘못된 비밀번호, 품절) → Coveo 에도 없음, 낮은 비율 가정
- 리뷰 작성(`PUT /rest/products/{id}/reviews`), 계정 화면

## 4-2. 매핑: OTTO 이벤트 → 팀 PHP 쇼핑몰

출처: team_one 커밋 `f952576` `web/src` — 라우트 `public/api/index.php`, 화면 흐름 `public/assets/app.js`.
구조가 Juice Shop 과 다르다: **페이지(.php)를 먼저 받고, 그 페이지의 app.js 가 `/api/v2/*` 를 부른다**(팀원 `orphan_api_ratio` 피처의 전제).
로그인 상태면 **모든 페이지 로드마다** 상단 장바구니 배지용 `GET /api/v2/cart` 가 붙는다(`renderNav → refreshCartBadge`).

| OTTO / 상황 | 팀 쇼핑몰 요청 (순서대로) | 비고 |
|---|---|---|
| 세션 시작 | `GET /products.php` → 정적(`/assets/app.js` 등) → `GET /api/v2/products` (+로그인 시 `GET /api/v2/cart`) | 목록 페이지가 진입점 |
| `click` | `GET /product.php?id={pid}` → `GET /api/v2/products/{pid}` (+`GET /api/v2/cart`) | 상세는 별도 페이지 |
| 첫 `cart` 직전 (비로그인) | `GET /login.php` → `POST /api/v2/login` → `GET /products.php` → `GET /api/v2/products` | 로그인 후 목록으로 이동(app.js `go('/products.php')`) — 원래 보던 상품으로 돌아가려면 `click` 한 번 더 |
| `cart` | `POST /api/v2/cart` `{product_id, quantity}` | 같은 상품 반복은 장바구니 화면에서 `PATCH /api/v2/cart/{product_id}` |
| `order` (장바구니에서) | `GET /cart.php` → `GET /api/v2/cart` → `POST /api/v2/orders` → `DELETE /api/v2/cart` → `GET /order.php?id={oid}` → `GET /api/v2/orders/{oid}` | 상세에서 바로 구매하면 `POST /api/v2/orders` 만 |
| (OTTO 에 없음) 내 주문 보기 | `GET /orders.php` → `GET /api/v2/orders/me?…` | 주문 이력이 있는 사용자에 낮은 비율로 삽입 |
| 검색 | `GET /api/v2/products/search?q=…` | OTTO 에 없음 → Coveo 비율 |

- **소유 자원**: `/api/v2/orders/{id}` 만 '주인만 봐야 하는 객체 ID'. `/api/v2/cart/{product_id}` 의 id 는 **상품 id**(공개)라 `uniq_objects` 대상이 아니다.
  → `features.py --owned-path /api/v2/orders/{id}` (Git Bash 면 `MSYS_NO_PATHCONV=1`). 팀 사이트의 BOLA 표적은 문서 밖 `/api/v1/users/{id}`.
- 상품 수: 팀 DB 의 상품 수로 `hash(aid) % N`. DB 스키마·시드가 레포에 없어(외부 DB 서버) 로컬에 띄우려면 `Repositories/*.php` 의 SQL 로 스키마를 직접 만들어야 한다.

## 5. 판정 실험 (이게 통과해야 의미 있음)

- 학습: 기존 생성기 정상 + OTTO 재생 정상 / 평가: `docs/33` 과 같은 **출발지 분할, 시드 5개**, 평가 정상은 **재생하지 않은 출발지**.

- 지름길 점검: `ml/shortcut_auc.py` 로 'OTTO 재생 정상 vs 생성기 정상'이 피처 하나로 갈리면, 재생 데이터가 또 다른 흔적을 남긴 것.
