# 04. SOAR 구현 계획 — 탐지 다음 단계 자동화

> 작성일: 2026-10-22 · 상태: 계획(초안)
> 목표: Wazuh 알럿·ML 이상 판정 이후의 **수집 → 보강 → 판단 → 조치 → 기록**을 자동화하고, LLM 의견을 안전하게 끼워 넣는다.
> 관련: `03_ML_vs_LLM_비교실험_계획.md` §3-6(자동 대응에 LLM 도입), `01_Wazuh_ML_실습_런북.md` Phase 3(자동 차단)

> **🔄 2026-10-22 변경**: 직접 구현(FastAPI) 대신 **기존 [`wazuh-slack-alertbot`](https://github.com/zeldaim/wazuh-slack-alertbot)을 확장**하는 방향으로 바꾼다. 수집·알림·중복 제거가 이미 실제 Wazuh와 연동돼 있기 때문. 단계별 대응표는 `06_기존자산_연계계획.md` §3. 아래 설계(판단 구간, 플레이북, LLM 안전장치, 실험)는 그대로 유효하다.

---

## 0. 한눈에

| 질문 | 결정(안) | 이유 |
|---|---|---|
| SOAR가 뭘 하나 | 탐지 **다음**의 조사·판단·조치를 자동화 | 지금 프로젝트는 "찾기"까지 완성 |
| 무엇으로 만드나 | **Python(FastAPI) 직접 구현**이 메인 | 가볍고(노트북 RAM), ML·LLM 연결 자유, 원리 설명 가능 |
| 오픈소스 SOAR는 | Shuffle을 **클라우드 단계 비교용**으로 | Wazuh 연동 사례 많고 화면이 좋지만 무거움 |
| LLM 역할 | 애매한 건만 **의견 제시**, 사람이 승인 | 로그 조작·오판 위험 때문 (03 §3-6) |
| 성과 측정 | 탐지→조치 시간(MTTR), 오차단 횟수 | SOAR 효과를 숫자로 |

## 1. 전체 흐름

```
Wazuh 알럿 / ML 이상 판정
        │
        ▼
 ① 수집 ── 알럿을 SOAR로 전달 (웹훅)
        │
        ▼
 ② 보강 ── IP 평판·위치, ML 점수, 과거 이력, 허용 목록 확인
        │
        ▼
 ③ 판단 ── 확실함 → 자동 조치 / 애매함 → LLM 의견 + 사람 승인 / 낮음 → 기록
        │
        ▼
 ④ 조치 ── 방화벽 차단(시간 제한), 계정·토큰 정지, 슬랙 알림
        │
        ▼
 ⑤ 기록 ── 사건 기록, 자동 해제, 처리 시간 측정
```

## 2. 구현 방법 비교

| 방법 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **A. 직접 구현 (Python + FastAPI)** | 가벼움, ML·LLM 연결 자유, 동작 원리 전부 설명 가능 | 화면·사건 관리 기능 직접 제작 | **메인** |
| B. Shuffle (오픈소스 SOAR) | Wazuh 연동 사례 많음, 드래그식 플레이북, 발표 화면 좋음 | 내부 저장소 포함이라 무거움 — 노트북 RAM에 부담 (실측 확인 필요) | 클라우드 단계 비교용 |
| C. TheHive + Cortex | 사건 관리·자동 분석기 강력, 실무 사용 많음 | 더 무겁고 설치 복잡 | 이번 범위 밖 |

→ A로 핵심을 만들고, 여유가 있으면 클라우드에서 B로 같은 플레이북을 재현해 **"직접 구현 vs 오픈소스 SOAR"** 비교.

## 3. 구성 요소 (A안)

```
soar/
├── app.py               # FastAPI: /alert 웹훅 수신, /approve 슬랙 버튼 콜백
├── playbooks/           # 플레이북 정의 (YAML)
│   ├── ssh_bruteforce.yaml
│   ├── api_enumeration.yaml
│   └── data_exfil.yaml
├── enrich/              # 보강: IP 평판·위치, ML 점수, 이력, 허용 목록
├── decide.py            # 판단: 점수 구간 → 자동/LLM+승인/기록
├── llm_advisor.py       # LLM 의견 (행동 목록 제한, 숫자 요약만 입력)
├── actions/             # 조치: Wazuh AR 차단, 토큰 정지, 슬랙 알림, 자동 해제
└── store.py             # 사건 기록 (SQLite), 처리 시간 측정
```

> 위 구조는 설계안이며 아직 구현되지 않았다.

### 3-1. 수집

- Wazuh 매니저의 **커스텀 연동(integration)** 기능으로 특정 레벨 이상 알럿을 SOAR 웹훅으로 전송
- ML 탐지기(`detector/wazuh_ml_detect.py`)는 이상 판정 시 같은 웹훅으로 전송하도록 확장

### 3-2. 보강

| 항목 | 출처 |
|---|---|
| IP 평판 | 공개 평판 DB (랩에서는 모의 데이터로 대체 가능) |
| 국가·사설 IP 여부 | GeoIP DB |
| ML 이상 점수 | ML 탐지기 |
| 과거 사건 이력 | SOAR 자체 기록 |
| 허용 목록 | 사내 서버·관리자 IP 설정 파일 |

### 3-3. 판단

| 구간 | 조건(예) | 처리 |
|---|---|---|
| 확실함 | ML 점수 상위 + 알려진 공격 패턴 + 허용 목록 아님 | **즉시 자동 조치** (LLM 안 거침) |
| 애매함 | 점수 중간 또는 근거 불충분 | **LLM 의견 + 슬랙 승인** |
| 낮음 | 그 외 | 기록만 |

- **허용 목록은 모든 판단보다 우선**한다.

### 3-4. 조치

- 모든 조치는 **되돌릴 수 있게** — 차단엔 반드시 만료 시간, 해제 기능 동시 구현
- 슬랙 메시지에 **[차단] [관찰] [무시]** 버튼 → 누른 사람·시각 기록

### 3-5. 기록·측정

- 사건마다: 알럿 시각, 보강 결과, 판단 구간, LLM 입력·답변, 승인자, 조치, 해제 시각
- **MTTR(탐지→조치 시간)** 자동 계산

## 4. 플레이북 (YAML로 정의)

플레이북을 코드가 아니라 **설정 파일**로 만들어, 새 시나리오를 추가할 때 코드를 고치지 않는다.

```yaml
# playbooks/ssh_bruteforce.yaml (예시)
name: ssh_bruteforce
trigger:
  source: [wazuh, ml]
  match: { rule_groups: [authentication_failed] }
enrich: [geoip, reputation, ml_score, history, allowlist]
decide:
  auto:     "ml_score >= 0.9 and not allowlisted"
  advisory: "ml_score >= 0.6"
actions:
  auto:     [{ block_ip: { ttl_min: 30 } }, notify_slack]
  advisory: [llm_advice, slack_approval]
```

### 4-1. SSH 브루트포스 (ML 실습 연결)

- 보강: 인증 실패 횟수, 시도 계정 수, 해외 IP 여부
- 판단: ML 점수 매우 높음 + 허용 목록 아님 → **30분 자동 차단**
- 조치: Wazuh Active Response 차단 → 슬랙 알림 → 30분 뒤 자동 해제

### 4-2. API 대입 조회 (`finance_secure` 런북/API대입공격_실습, 신한 사례)

- 보강: 한 계정이 조회한 서로 다른 고객 수, 조회 성공률
- 판단: 애매하면 LLM이 "정상 업무 패턴인지" 의견 → 슬랙 버튼으로 승인
- 조치: 해당 계정 API 토큰 정지, IP 레이트리밋 강화

### 4-3. 데이터 대량 유출 (모니터링 지표)

- 보강: 서버 송신량, 평소 대비 배수, 목적지 IP
- 판단: 서비스 영향이 커서 **자동 조치 없음**, 사람 승인만
- 조치: 목적지 차단, 담당자 호출

## 5. LLM 의견 단계의 안전장치

`03` §3-6과 동일한 원칙을 SOAR에서 강제한다.

1. **행동 목록 제한** — 출력은 `block_30m | observe | ignore` + 이유 문장만. 형식이 다르면 무시하고 사람에게 넘김
2. **되돌릴 수 있는 조치만** — LLM 추천으로는 영구 차단 불가
3. **숫자 요약만 입력** — 로그 원문(공격자가 쓸 수 있는 칸) 대신 정리된 수치 → 로그 조작 위험 감소
4. **허용 목록 우선** — LLM 판단보다 앞에서 걸러냄
5. **전부 기록** — 입력·답변·최종 조치

## 6. 실험

| 실험 | 비교 | 측정 |
|---|---|---|
| 자동화 효과 | 수동 대응 vs SOAR | 탐지→조치 시간(MTTR) |
| LLM 의견 효과 | SOAR 단독 vs SOAR + LLM | 정상 IP 오차단 횟수, 공격 놓친 횟수 |
| 로그 조작 내성 | LLM에 원문 전달 vs 숫자 요약 전달 | 조작 문장에 속은 비율 |
| (선택) 구현 방식 | 직접 구현 vs Shuffle | 구축 시간, 자원 사용량, 플레이북 작성 난이도 |

## 7. 단계별 할 일

| 단계 | 내용 | 산출물 |
|---|---|---|
| 1 | FastAPI 웹훅 + Wazuh 커스텀 연동으로 알럿 수신 | 수신 로그 |
| 2 | 보강(GeoIP, 허용 목록, ML 점수) | 보강된 사건 JSON |
| 3 | 플레이북 YAML 로더 + 판단 구간 | SSH 브루트포스 플레이북 동작 |
| 4 | 조치: Wazuh AR 차단 + 만료 해제 + 슬랙 알림 | 차단·해제 데모 |
| 5 | 슬랙 승인 버튼 + LLM 의견 | 애매한 사건 승인 흐름 |
| 6 | 기록·MTTR 측정 | 사건 DB, 측정표 |
| 7 | 실험(§6) 및 정리 | 결과 표, 발표 데모 |

## 8. 주의

- 자동 차단은 **랩 안에서만**. 오탐 시 정상 IP를 끊을 수 있다.
- 슬랙 봇 토큰·LLM API 키는 코드에 넣지 말고 환경변수로, 저장소에 올리지 않는다.
- LLM에 보내는 데이터는 랩 데이터만 사용 (외부 API 사용 시 실데이터 전송 금지).
