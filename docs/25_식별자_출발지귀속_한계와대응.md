# 25. 식별자·출발지 귀속 한계와 대응 (웹 NAT + DB 귀속 통합)

> 작성일: 2026-10-25 · 발표/적용 한계 정리.
> 한 문장: **우리 모델은 IP를 "피처"가 아니라 "행위 주체를 묶는 키"로 쓴다. 로그에 찍힌 식별자가 실제
> 행위자와 다른 환경에선 그 키가 깨진다.** 해법은 "더 강한 식별자로 키를 올리거나, 축을 바꾸는 것".

## 1. 근본 문제 — "로그의 식별자 ≠ 실제 행위자"

웹과 DB가 **같은 문제**다:
- 웹: NAT/프록시/CDN 뒤에선 서버가 **실 클라이언트가 아닌 중간 IP**만 봄. XFF를 믿으면 **조작 가능**.
- DB: DB는 보통 **앱 서버(커넥션 풀) 하나**만 봄 → 누가 쿼리한 실제 사용자인지 모름. (`docs/14` §4, `docs/22`)

> IP는 **그룹핑 키**일 뿐(피처 아님). 피처(요청률·다양성·엔트로피·상대값)는 **무엇으로 묶든 그대로 동작** → 키만 바꾸면 방법은 유지.

## 2. 그룹핑 키가 깨지는 환경

| 환경 | 문제 | 결과 |
|---|---|---|
| NAT·회사프록시·CGNAT | 다수 사용자 = 한 IP | 행위 뭉침(오탐) / 공격자 은닉 |
| CDN·LB·리버스프록시 | 실 클라이언트 IP 안 보임 | 전원이 한 주체로 |
| XFF 변조 | 앱이 XFF 신뢰 시 가짜 IP 주입 | 그룹핑 오염 |
| IP 로테이션·봇넷·Tor | 공격 분산 | 주체별 저활동 → 임계 밑 회피 |

## 3. 대응 — 키를 올리거나 축을 바꾼다

1. **식별자 승격(UEBA)**: IP → **인증 사용자 ID / JWT `sub` / 세션 / API 키 / 계정**. NAT·로테이션 뚫음. (상대피처 §K도 사용자 키일 때 최적)
2. **축 전환**: 공격자 중심(IP) → **피해자/자원 중심·전역 집계**. "이 계정이 어느 IP에서든 실패 N회", "이 엔드포인트가 전체적으로 공격받나".
3. **티어/서비스 단위 후퇴**: 식별자가 아예 없으면 티어 전체 이상탐지(= DB 귀속 옵션 C, `edge/correlate.py`).
4. **DB 전용**: 앱이 **사용자 ID를 쿼리 주석/세션에 심기**, 또는 웹-DB 로그 시간 상관(`correlate.py`).

## 4. "회피가 그 자체로 이상징후인가?" — 반만

- **되는 경우**: 한 축 회피가 **다른 축에 흔적**. 한 계정이 1h에 50 IP 로그인(계정 키로 이상)·XFF 값이 매번 바뀜(패턴 이상)·분산이나 한 피해 자원에 집중(피해자 축 이상).
- **안 되는 경우(진짜 갭)**: 완전 분산 low-and-slow(IP마다 1회, 계정 없음)는 **모든 주체별 관점 회피** → 행위 ML만으론 못 잡음. **전역 집계·위협 인텔·레이트 상관**이라는 별도 층 필요.

## 5. 지금 할 수 있는 것 vs 나중 vs 근본 갭

| 구분 | 내용 | 상태 |
|---|---|---|
| **지금 랩 재현 가능** | NAT(다수 사용자 한 IP)·XFF 변조·IP 로테이션 시뮬 / **키를 사용자로 올리면 낫다는 증명** | 공격 재현과 동일 방식 — 하면 됨 |
| **실제 인프라 필요** | 팀의 진짜 NAT 토폴로지·실 사용자 인증 로그로 검증 | 팀 인프라 후 |
| **근본 갭(설계 추가)** | 완전 분산 low-and-slow | ML만으론 X → 전역 집계 층 설계 필요 |

> 결론: **"재현 안 하면 못 푼다"가 아니다.** 대부분 랩에서 재현·증명 가능(공격처럼), 실제 검증만 팀 인프라 후,
> 딱 하나(완전 분산)만 탐지 층 추가가 필요하다. → 발표에선 "적용 한계와 대응"으로 정직하게 제시.

## 6. 다음에 재현한다면 (실험 설계)
- 정상 사용자 N명을 **한 IP(NAT)** 뒤에 두고, 그 틈에 공격자 1명 → IP 키로는 못 잡고 **사용자 키로는 잡힘** 비교.
- XFF를 매 요청 랜덤으로 바꾸는 공격 → IP 키 그룹핑 붕괴 재현, XFF 엔트로피로 역탐지.
- 같은 공격을 **M개 IP로 분산**(IP당 소량) → 주체별 회피 재현, 전역 집계로 탐지.
