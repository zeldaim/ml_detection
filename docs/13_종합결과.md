# 13. 종합 결과 — 룰이 놓친 이상행위를 ML로 탐지 (웹·DB 2계층)

> 작성일: 2026-10-24 · 상태: 랩 실험 완료(합성·소규모), 자동화 파이프라인 동작 확인
> 환경: Juice Shop + nginx (Wazuh 없이 직접 수집), scikit-learn 1.9.1, Python 3.12/3.15

## 0. 한 줄 결론

방화벽·룰이 못 거르는 **앱/DB 계층 이상행위**(BOLA·SQLi·느린 공격)를, **비지도(IF+LOF)가 발견하고 지도(RF)가 종류를 붙이는 2계층 ML**로 잡았다. 특히 **느린 공격은 IF가 놓치고 LOF가 잡아** 둘을 함께 써야 하는 근거를 웹·DB 양쪽에서 확인했다.

## 1. 목표와 범위

- **탐지 대상:** 방화벽/WAF를 통과하는 앱 로그 — 문법은 정상인데 패턴이 공격(BOLA 열거, 느린 대입, SQLi, 대량 수집)
- **왜 ML:** 룰은 "아는 공격"만 잡는다. 룰이 놓친·처음 보는 공격을 비지도 ML이 "평소와 다름"으로 보완
- **학습 데이터는 전체 로그(archives/nginx 직접)** — alerts(룰 통과분)로 학습하면 룰 흉내만 낸다 (`docs/08` §2-4-1)

## 2. 구축한 것

```
[공격자/AI 에이전트] ─▶ Juice Shop(PHP형 쇼핑몰 API) + nginx + (MySQL)
                           │ 로그
                           ▼
   웹: nginx access.log ─┐
   DB: MySQL general log ┤─▶ 피처(IP×5분) ─▶ IF·LOF(발견) + RF(종류) ─▶ 경보
                         │                      저장모델 .joblib
   자동화: consumer/(단순) · edge/(엣지 피처+중앙 collector)
```

| 영역 | 파일 |
|---|---|
| 피처·모델 | `ml/features.py`, `ml/models.py`, `ml/supervised.py`, `ml/classify_type.py` |
| 모델 저장/판정 | `ml/train_export.py`, `ml/predict.py`, `models/model.joblib`(웹), `models/db_model.joblib`(DB) |
| 트래픽 생성 | `tools/gen_normal_traffic.py`, `tools/gen_attack_traffic.py`, `tools/gen_db_traffic.py` |
| 자동 수집 | `consumer/`(단순), `edge/`(엣지 피처 추출 + DB 보안) |

## 3. 웹 계층 결과

정상 6 IP 40분(37구간) + 공격 4사건(빠른 대입 ×2, BOLA ×2[빠름/느림]). contamination 0.05 고정(공격 보기 전 정상 로그로 결정).

**E2 — 처음 보는 공격 (종류 통째로 빼고 학습):**

| 모델 | 탐지율 | 정상 오탐률 |
|---|---|---|
| RF | 0.29 (2/7) | 0.00 |
| IF | 0.43 (3/7) | 0.00 |
| **LOF** | **1.00 (7/7)** | 0.00 |
| IF\|LOF | 1.00 | 0.00 |
| RF\|IF\|LOF | 1.00 | 0.00 |

- **IF가 놓치고 LOF가 잡은 구간 4개** (느린 BOLA) → 가설 H5 확인
- RF는 학습에 없던 종류라 0.29 (처음 보는 공격은 지도학습이 약함)

**E3 — 정상만 있을 때 오탐률:** IF·LOF 2/37(5%, contamination 0.05), 룰 0/37, OCSVM 7/37

**종류 분류(RF 다중):** 3/7 — 빠른 대입·빠른 BOLA는 정확, 느린 BOLA는 "정상"으로 오판(포착 자체 실패). 대입↔BOLA 혼동은 0.

## 4. DB 계층 결과 (웹과 같은 경향 재현)

정상 6 IP + 공격 6사건(BOLA·SQLi·대량수집 각 2). DB 피처는 쿼리 로그에서: `distinct_where_ids`(소유 테이블 id 범위=BOLA), `sqli_token_hits`(UNION·sleep·information_schema 등), `q_count`·`uniq_templates`(대량수집), `interval_cv`(AI 간격).

**E2:**

| 모델 | 탐지율 | 정상 오탐률 |
|---|---|---|
| IF | 0.78 (7/9) | 0.25 |
| **LOF** | **1.00 (9/9)** | 0.12 |
| IF\|LOF | 1.00 | 0.25 |

- **IF가 놓치고 LOF가 잡은 구간 2개** (느린 BOLA) → H5가 DB 계층에서도 확인
- **종류 분류:** 5/9 — SQLi·대량수집 정확, 느린 BOLA 일부 오판 (웹과 동일 패턴)

## 5. 핵심 결론 — 2계층 탐지 구조

```
1층 발견(비지도):  IF(전역 이상) + LOF(국소 이상)  → 느린·처음 보는 공격까지
2층 분류(지도):    RF                              → 포착된 공격의 종류 이름
```

- **한쪽만으론 부족:** RF만 → 처음 보는/느린 공격 놓침. IF/LOF만 → 종류를 모름. 합쳐야 발견+식별.
- **LOF가 IF를 보완:** 느린 공격은 전체적으로 안 튀어 IF가 놓치지만 LOF가 국소 밀도로 잡음 (웹 4구간·DB 2구간).
- **웹·DB 양 계층에서 같은 결론** → 데이터센터 다계층 탐지의 축소판.

## 6. 자동화 (수동으로 로그 주지 않음)

| 방식 | 디렉토리 | 특징 |
|---|---|---|
| 단순 소비자 | `consumer/` | 중앙이 원본 로그를 읽어 저장모델로 반복 판정 |
| 엣지 + DB | `edge/` | 각 호스트가 **피처 벡터만** 전송(원본 로그 안 나감), 중앙 collector가 모델 판정 |

엣지 이점: 대역폭·개인정보(원본 쿼리 미전송), 다중 호스트 확장. collector가 웹·DB 벡터를 한 곳에서 판정 → SOC 축소판.

## 7. 한계 (정직하게)

- **합성·소규모 데이터**: 종류·사건이 적어 수치는 "경향 확인"이지 확정 성능이 아니다. 실제 로그로 재검증 필요.
- **오탐률**: 정상만으로도 IF·LOF는 5~12% 경보 → 결과엔 탐지율과 오탐률을 항상 같이 본다.
- **DB 출발지 구분**: DB 사용자가 하나면 쿼리를 IP별로 나누기 어려움 — 실제 적용 시 보강.
- **느린 공격 분류**: 발견(LOF)은 되지만 RF 종류 분류는 약함.
