# 32. 피처 선택 원칙 — 몇 개를, 어떻게 정하나 (공격별이 아니라 축별)

> 작성 2026-10-26. 팀 질문 정리: "한 공격에 피처를 너무 많이 넣으면 안 된다(오탐)" → 그럼 **공격별로 피처를 정해 두나, 정하고 찔러보고 다시 정하나?** **피처는 많을수록 좋지 않나?** **엣지 에이전트는 DB 에만 두면 안 되나?**
> 관련: `docs/27`(web_v1 확정·소거 실험 — 이 문서의 수치 근거), `docs/21`(개발 단계 실험), `docs/26`(신호별 결정 로직), `docs/14` §4·`docs/25`(출발지 귀속), `docs/29`(수집 경로), `edge/README.md`.

## 0. 답

| 질문 | 답 |
|---|---|
| 공격별로 피처를 정해 두나? | **아니다.** 모든 공격에 **공통인 한 세트**(`web_v1` 10개)를 **행위의 축**별로 고르고 고정한다. 공격별 피처 = "그 공격이 올 걸 안다" = 룰 방식 |
| 정하고 찔러보고 다시 정하나? | **개발 단계에선 그렇다**(`docs/21`). 그다음 **동결**(`docs/27`)하고, 운영에선 바꾸지 않는다. 바꾸려면 새 버전(`web_v2`)으로 처음부터 재검증 |
| 피처는 많을수록 좋나? | **아니다. 적으면 못 보는 공격이 생기고, 많으면 정상을 공격으로 본다.** 기준은 개수가 아니라 **서로 다른 축을 빠짐없이, 축마다 대표 한두 개** |
| 더 넓게 보려면? | 한 모델에 피처를 쌓지 말고 **신호 출처별로 모델을 나눈다** — 웹 `web_v1` / DB `db_v1` / 호스트 `host_v1` |
| 엣지 에이전트는 DB 에만? | **배치는 DB 에만으로 충분하다(오히려 맞다).** 하지만 **탐지를 DB 로만 하면 안 된다** — 웹 로그는 원문 그대로 수집(§5) |

## 1. 피처가 정해지는 과정 — 개발 → 동결 → 운영

```
개발 (반복)                         동결                                  운영 (고정)
피처 넣기 → 공격 → 평가 → 빼기/넣기  drop-one 소거 실험, seed 10개 평균     같은 10개 + 저장 모델로 판정
docs/21 (seq_id_score 거부,         → web_v1 10개 확정 (docs/27)          처음 보는 공격도 같은 10개로
ssh_fail 분산 0 제외 …)              기존 셋은 고치지 않음, 바꾸면 web_v2    (docs/30)
```

- **반복 실험의 함정:** 찔러보고 다시 정하기를 끝없이 하면 **우리가 아는 공격에 맞춘 피처**가 된다(시험 문제 보고 공부하기). 우리 공격 점수는 오르지만 처음 보는 공격엔 떨어진다.
- 그래서 규칙 3개:
  1. 피처를 고를 때 쓴 공격과 **평가하는 공격을 분리**(held-out, `docs/20`·`docs/24`)
  2. 정해지면 **동결** — 운영 중 공격마다 피처를 바꾸지 않는다
  3. 바꿀 땐 **새 이름**(`ml/feature_spec.py` 에 `web_v2`)으로 추가하고 소거 실험부터 다시
- 근거: 학습·선택에 쓰지 않은 `boost_bola_slow`(새 IP 6개, 36구간)를 고정된 `web_v1` + v3.1 로 **36/36** 탐지 (`docs/30` §3)

## 2. 축 — 공격 이름이 아니라 행위로 고른다

| 축 | `web_v1` 피처 | 주로 드러나는 공격 |
|---|---|---|
| 양·속도 | `req_count`, `max_req_1min` | 무차별 대입, 스크래핑 |
| 평소 대비 배수 (UEBA) | `rel_req_count`, `rel_max_req_1min` | 계정 탈취 후 급증(평소엔 느린 사용자) |
| 객체 다양성 | `uniq_objects`, `uniq_paths` | BOLA, 열거 |
| 실패 | `err_ratio` | 추측, 스캔 |
| 규칙성·내용 | `interval_cv`, `endpoint_entropy` | 봇, 느린 자동화 |
| 쓰기 | `write_ratio` | BFLA |

처음 보는 공격도 **어느 축에선가 평소와 다르게** 나오면 비지도 모델(IF·LOF·AE)이 잡는다. RF 가 붙이는 이름은 학습한 종류 중 가장 닮은 것일 뿐(`docs/30` §3).

## 3. 피처가 적을 때 / 많을 때

### 3-1. 적으면 — 그 축의 공격이 안 보인다
모델은 피처에 없는 것을 못 본다. 예를 들어 `req_count`·`max_req_1min`·`err_ratio` 3개뿐이면:
- 느린 BOLA — 양도 실패도 평소와 같다. `uniq_objects` 가 없으면 안 보인다
- 일정 간격 봇 — `interval_cv` 가 없으면 안 보인다
- 권한 밖 쓰기(BFLA) — `write_ratio` 가 없으면 안 보인다

실측: `docs/27` 소거 실험에서 **`uniq_objects` 하나를 빼면 IF|LOF|AE 0.91 → 0.78**, `max_req_1min` 을 빼면 0.82.

### 3-2. 많으면 — 정상이 공격처럼 보인다
1. **같은 축을 여러 개** 넣으면 새로 보이는 건 없고 그 축의 무게만 커진다. 요청 수·1분 최대·10초 최대·바이트 수는 모두 "양" → 양만 많은 정상(대량 주문, 이벤트 기간)이 이상으로 찍힌다
2. **관계없는 피처**는 정상의 흔들림만 더한다. 그중 한 칸만 튀어도 이상 판정 → 오탐 ↑. 또 LOF 처럼 거리로 판단하는 모델은 의미 없는 차원이 많을수록 모든 점 사이 거리가 비슷해져 공격이 덜 튄다(차원의 저주)
3. **평소를 배울 데이터가 모자란다.** 지금 정상 학습 구간은 149개(`docs/27` §2). 피처가 늘면 배워야 할 경우의 수가 커진다

실측: 분산 0 인 `ssh_fail` 을 빼자 앙상블 오탐 **0.002 → 0.000** (`docs/27` §2).

## 4. 피처를 넣을지 정하는 기준

1. **기존 축으로 안 보이는 공격이 있는가?** 있으면 추가 이유(커버리지). 예: `write_ratio` — 지금 데이터엔 BFLA 가 없어 효과를 못 쟀지만 BFLA 를 맡을 피처가 따로 없어 유지
2. **이미 있는 피처와 같은 축인가?** 같으면 넣지 않는다
3. **넣었을 때 오탐이 늘지 않는가?** drop-one 소거 실험으로 확인 — 역할 판정 규칙(탐지/오탐억제/중립/커버리지)은 `docs/27` §1
4. **분산 0 이면 제외** — 정보도 없고 검증도 못 한다
5. **식별자·원문은 넣지 않는다** — IP·사용자 id 를 피처로 쓰면 "누구냐"를 외워 누수(`docs/27` §0)

## 5. 더 넓게 보려면 — 출처별 모델 (그리고 엣지 에이전트 배치)

### 5-1. 한 모델에 쌓지 말고 나눈다

| 모델 | 피처 | 웹 로그가 못 보는데 이게 보는 것 |
|---|---|---|
| 웹 `web_v1` | 10 | (주 입력 — API 행위) |
| DB `db_v1` | 8 (`edge/db_features.py`) | 실제 실행된 SQLi(`sqli_token_hits`), 정확한 레코드 접근 수(`distinct_where_ids`), 대량 읽기 |
| 호스트 `host_v1` | 12 (`edge/host_metrics.py`) | 채굴·연결 폭주·유출 같은 자원 남용 |

각 모델은 작고 정확하게, 전체 시야는 넓게 — 30개를 한 모델에 넣는 것보다 오탐이 적다는 게 설계 의도다. **단 지금 운영 후보는 웹뿐**: `db_v1` 은 합성 DB 소거에서 앙상블 오탐 0.31(운영급 아님, 실제 MySQL 후 v2), `host_v1` 은 역할이 가설(`docs/27` §0). 반대로 웹+DB 를 한 행으로 합치는 `edge/correlate.py --mode join`(웹 9 + db 8 = 17)은 출발지 귀속을 위한 것이고, 합성에서 동작 확인만 됐다(`docs/14` §4).

### 5-2. 엣지 에이전트는 DB 에만 두면 안 되나?

**배치는 DB 에만 — 맞다.** 엣지(호스트에서 피처로 요약해 숫자만 보냄)가 **꼭 필요한 곳**이 DB 다.

| 호스트 | 수집 방식 | 이유 |
|---|---|---|
| **DB VM** | **엣지** — `edge_agent.py --kind db` 또는 실험 단위 `db_features.py` → 숫자만 | 쿼리 원문 = 개인정보. **원문은 DB VM 밖으로 안 나감**(`docs/29` §0·§5) |
| 웹 VM | **원문 그대로** — Filebeat → Logstash → `inbox/live/` | 원문이 있어야 피처를 바꿔도 다시 뽑는다(§1 의 web_v2 재검증). 엣지로 숫자만 보내면 재추출 불가(`docs/29` §3) |
| 호스트 지표 | node_exporter(→ Prometheus) | 이미 숫자 — 엣지 불필요 |

→ `edge_agent.py --kind web` 은 있지만 **지금 설계에선 쓰지 않는다**(원문 수집과 중복). 대역폭·원문 반출이 문제가 되는 환경일 때만 대안.

**하지만 탐지를 DB 로만 하면 안 된다.**
1. **DB 는 공격자를 구분 못 한다.** PHP 앱이 계정 하나로 접속하므로 Connect host 가 전부 `app@10.16.1.10`(`docs/14` §4) → "DB 티어 전체가 이상한가"만 판정(`correlate.py --mode tier`), 출발지 해상도를 잃고 오탐 ↑. 누구를 차단할지(IP·사용자)도 DB 엔 없다
2. **DB 에 닿지 않는 공격이 있다.** 없는 경로 스캔(404), 인증 실패 반복, 앱이 소유권 검사로 거절한 BOLA 시도, 캐시 응답, 정적 파일 — 쿼리가 안 생기거나 정상 쿼리와 같다. HTTP 상태·경로·간격은 웹 로그에만 있다
3. **웹 축 피처가 사라진다.** `err_ratio`(HTTP 상태), `endpoint_entropy`(API 경로), `rel_*`(사용자 평소 배수)는 웹 로그에서만 나온다

정리: **웹 = 원문 수집해 주 탐지, DB = 엣지로 숫자만 보내 보강**, 둘을 출발지로 잇는 건 `correlate.py --mode join`(웹 IP 행에 같은 구간 db_* 결합). DB 엣지만 남기고 웹을 빼면 §3-1 의 "적으면 못 본다"가 축 통째로 일어난다.
