## 0. 왜 별도 phase인가

웹과 **데이터 민감도·출발지 귀속·로그 소스가 근본적으로 달라서** 한 바퀴에 섞으면 안 된다.
웹 계층 파이프라인(피처→모델→플라이휠)이 실제 데이터로 안정된 뒤, 같은 틀을 DB에 **독립적으로** 적용한다.

## 1. 실무에서 DB 보안은 어떻게 하나

핵심은 **쿼리 계층을 본다**(WAF가 못 보는 것).

| 방식 | 무엇 | 도구/기능 |
|---|---|---|
| DAM (Database Activity Monitoring) | 모든 쿼리 가로채 감사·탐지·차단 | Imperva, IBM Guardium, DataSunrise |
| 네이티브 감사 로그 | DB가 직접 쿼리 기록 | MySQL `audit_log`/general log, PostgreSQL `pgAudit`, Oracle Unified Audit |
| 클라우드 관리형 | 매니지드 DB 감사 → SIEM | AWS RDS/Aurora Audit, GCP Cloud SQL, Azure SQL Audit |
| 쿼리분석·UEBA | 쿼리/사용자 행위 이상 | 평소와 다른 테이블·대량 추출·심야 접근 |
| 프록시형 | 앱↔DB 사이 검사 | ProxySQL + 룰, DataSunrise |

**실무가 탐지하는 행위 ↔ 이 프로젝트 DB 피처 (`edge/db_features.py`)**
- SQLi: UNION·주석·`information_schema`·`sleep()`/`benchmark()` → `sqli_token_hits`
- BOLA/과다추출: 남의 레코드 id 다수 조회 → `distinct_where_ids`, `q_count`
- 권한오용·심야: 평소 안 쓰던 테이블/시간 → `distinct_tables`, `interval_cv`

> **실무 최대 난관 = 출발지 귀속**: DB는 보통 앱 서버 하나(커넥션 풀)만 보여 공격자 식별이 흐려짐.
> 해법: ① 앱이 사용자 ID를 쿼리 주석/세션에 심기 ② 웹-DB 로그 시간 상관 ③ 티어 단위 탐지.
> → `docs/14` §4, `edge/correlate.py`가 다루는 문제.

## 2. LLM에 DB 데이터를 맡길 때의 보안 이슈 (중요)

DB 원문은 웹 로그보다 훨씬 민감 → **원문을 외부 LLM에 보내면 안 된다.**

| 위험 | 왜 |
|---|---|
| 민감정보 유출 | 쿼리에 실제 값(`WHERE ssn=`, email, 카드, 해시)·`SELECT *` 결과 |
| 규정 위반 | 외부 전송 = 국외이전·제3자 제공 (PIPA·GDPR, 데이터 레지던시) |
| 벤더 보존/학습 | no-train·무보존 계약 없으면 저장·학습 위험 |
| 로그→프롬프트 인젝션 | 공격자가 쿼리에 심은 문자열이 LLM 지시로 둔갑 |
| 스키마 노출 | 테이블·컬럼 구조가 공격 지도 |

**규칙: DB 원문은 경내(on-prem), LLM엔 숫자 피처만.**
- ✅ `distinct_where_ids=52, sqli_token_hits=7, q_count=300`
- ❌ `SELECT * FROM users WHERE id=...`
- 방어: ① 피처화=자연적 비식별화(이미 함) ② 값 마스킹 `normalize()`(이미 함) ③ 민감 환경은 로컬/자체호스팅 LLM ④ no-train·출력제한. → `explain_llm.py`가 웹에서 쓰는 "숫자만 전송" 원칙을 DB에 그대로.

## 4. 착수 시 단계 (웹 플라이휠과 동형)

1. 합성 DB 바퀴: `gen_db_traffic.py` → `db_features.py` → `supervised.py`(DB 교차검증) — 틀 재확인
2. 실제 MySQL general log 수집(`docs/14` 런북) → 파서 점검(`--check`) → 출발지 귀속(`correlate.py`)
3. DB 플라이휠 누적셋 `dataset_db.csv` 시작(`accumulate.py`, 스키마 분리) + 모델 버전 보존
4. 웹과 **같은 결론 재현되나**: 느린 공격 LOF/AE 보완, SQLi는 토큰 피처, 분포 shift 주의
