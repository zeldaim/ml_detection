# 08. 테스트 환경 구축 순서 (쇼핑몰 타겟 + Wazuh + ML)

> 작성일: 2026-10-22 · 상태: 계획(초안)
> 목표: 쇼핑몰 타겟 서버에서 **정상·공격 로그**를 발생시키고, Wazuh로 수집해 **ML 이상 탐지**의 입력(alerts.json + archives.json)을 만든다.
> 전제: 기존 Home SOC Lab(VMware + Rocky 9 + Docker Wazuh 4.9.0 + ELK, Kali) 재사용.
> 역할: 환경 구축은 환경 팀, ML·LLM 분석은 분석 담당.

---

## 0. 전체 구조

```
[타겟 VM] Rocky/Ubuntu
  - OWASP Juice Shop (쇼핑몰 웹앱, Docker)
  - 웹서버 접근 로그 (nginx 또는 앱 로그)
  - SSH 서비스
  - Wazuh 에이전트
       │ (로그 수집)
       ▼
[Wazuh 매니저] (기존 Home SOC Lab)
  - 룰 분석 → alerts.json (룰에 걸린 것)
  - logall_json → archives.json (전체 로그)
       │
       ▼
[ML/LLM] 분석 담당 (alerts.json + archives.json 입력)

[Kali] ── 공격 ──▶ 타겟 VM
```

## 1. 왜 이 구조인가 (논의 결과)

- **ML을 쓰는 이유**: 룰(Wazuh)은 "아는 공격"만 잡는다. 느린 공격·BOLA·새로운 공격은 룰이 침묵 → ML이 "평소와 다른 행동"으로 보완
- **alerts vs archives 둘 다 쓰는 이유**: alerts.json은 룰이 거른 것만 → ML이 "룰이 놓친 것"을 보려면 전체(archives.json)가 필요. 둘을 비교하는 것이 실험
- **정상 로그는 우리 랩에서**: 비지도 학습의 "정상 기준"은 우리 환경 로그로 세워야 한다(공공데이터로 대체 불가). 이상 데이터는 소량(채점용)이면 충분
- **공공데이터(CSIC) 섞기 제외**: 비지도 학습엔 정상 기준만 있으면 되므로 데이터 합성이 불필요

## 2. 구축 순서

### 2-1. 타겟 서버 준비
- [ ] 타겟 VM 1대 준비 (Wazuh 매니저와 별도)
- [ ] Docker 설치
- [ ] **OWASP Juice Shop 배포**: `docker run -d -p 3000:3000 bkimminich/juice-shop`
- [ ] 브라우저로 `http://<타겟IP>:3000` 접속 확인
- [ ] SSH 서비스 활성화 (정상/공격 로그인 로그용)

> Juice Shop은 의도적 취약 앱 → **내부 랩에서만**. 외부 노출 금지, 보안그룹/방화벽으로 팀 IP만 허용.

### 2-2. 웹 접근 로그 확보
- [ ] Juice Shop 앞에 **nginx 리버스 프록시**를 두고 접근 로그 남기기
  - 또는 Juice Shop 자체 로그를 파일로 출력
- [ ] 로그 형식 확인: 시각·IP·메서드·경로·상태코드·크기 (combined 형식 권장)

### 2-3. Wazuh 에이전트 연동
- [ ] 타겟에 Wazuh 에이전트 설치, 매니저에 등록
- [ ] `ossec.conf`에 로그 소스 추가:
  - SSH/인증: `/var/log/secure` 또는 `/var/log/auth.log`
  - 웹 접근: nginx 로그 경로 (`<localfile>`로 추가)
- [ ] 매니저에서 에이전트 연결 확인 (`agent_control -l`)

### 2-4. 전체 로그 저장 켜기 (archives.json)
- [ ] 매니저 `ossec.conf`에서 `<logall_json>yes</logall_json>` 설정
- [ ] `archives.json` 생성 확인
- [ ] **디스크 주의**: 과거 디스크 풀 장애 이력 있음 → 실험 기간만 켜고, 로테이션/용량 모니터링

### 2-5. 룰 확인 (기존 자산 재사용)
- [ ] SSH 브루트포스 룰 100001 (60초 5회) 동작 확인
- [ ] 웹 공격 룰 필요 시 추가 (SQLi 100005 등)
- [ ] `wazuh-logtest`로 룰 발동 확인

## 3. 정상 로그 만들기

> "정상 기준"의 재료. 공격 없이 **정상만** 발생시킨다.

| 방법 | 내용 |
|---|---|
| 자동 스크립트 | 정상 사용자 행동 반복: 상품 목록 → 상세 → 검색 → 로그인 → 장바구니 → 주문 조회. `cron`으로 밤새 실행 |
| 직접 사용 | 가끔 정상 SSH 로그인, 웹 둘러보기 |
| 서버 기본 로그 | cron·세션·서비스 등 배경 정상 로그 |

- [ ] 정상 행동 목록 확정 (분석 담당과 함께 — 어떤 피처를 뽑을지와 연결)
- [ ] 정상 수집 기간 확보 (최소 몇 시간~1일, 길수록 좋음)
- [ ] **이 기간엔 공격 금지** (기준이 오염되지 않게)

## 4. 공격 로그 만들기 (Kali → 타겟)

> 정답지(언제·무엇을)를 반드시 기록.

| 공격 | 도구 | 잡히는 룰 |
|---|---|---|
| SSH 브루트포스(빠른) | Hydra | 100001 발동 예상 |
| SSH 브루트포스(느린, 간격 20초↑) | Hydra | 룰 침묵 예상 → ML 대상 |
| 포트 스캔 | Nmap | 100004 |
| 웹 공격(SQLi/XSS) | sqlmap 등 | 웹 룰 |
| BOLA/대량 조회 | 스크립트 | 룰 침묵 예상 → ML 대상 |

- [ ] **공격 시간대를 정상과 분리** (예: 정상 수집 후, 정해진 시간에만 공격)
- [ ] 정답지 기록: 시각·출발지·공격 종류·대상 (→ 채점에 사용)

## 5. ML/LLM 입력 넘기기 (분석 담당)

- [ ] `alerts.json` 경로 공유 (룰에 걸린 것)
- [ ] `archives.json` 경로 공유 (전체 로그)
- [ ] 정답지(answer) 공유
- [ ] 로그에 실제 비밀번호·개인정보가 없는지 확인 후 전달

## 6. 체크리스트 요약

```
[ ] 타겟 VM + Docker + Juice Shop
[ ] 웹 접근 로그 (nginx)
[ ] Wazuh 에이전트 연동 (SSH + 웹 로그)
[ ] archives.json 켜기 (디스크 주의)
[ ] 룰 동작 확인 (100001 등)
[ ] 정상 로그 수집 (공격 없이, 기간 확보)
[ ] 공격 로그 생성 (Kali, 시간 분리, 정답지)
[ ] alerts.json + archives.json + 정답지 → 분석 담당
```

## 7. 분석 담당이 병행할 것 (환경 안 기다리고)

- [ ] 랩 01 구조로 **피처 추출 코드** 미리 작성 (로그 → 사용자×5분 피처)
- [ ] Isolation Forest 외 모델(LOF, One-Class SVM)도 비교할 수 있게 틀 만들기
- [ ] LLM 분석 연결(ML 결과 → LLM 설명)
- [ ] 환경 로그가 오면 바로 넣을 수 있게 입력 형식 약속 (`access.log`/`answer.csv`)

> 코드를 먼저 완성해두면, 환경 팀의 수집 시간이 짧아도 바로 결과가 나온다.
