# 05. 데이터 전략 · 추천 시나리오 · 팀 분담

> 작성일: 2026-10-22 · 상태: 계획(초안)
> 문제: ML이 "평소"를 알려면 이벤트 데이터가 쌓여야 하는데, 시간이 부족하고 우리는 모의 분석 단계다.
> 해법: **공개 데이터로 "평소"를 빠르게 채우고, 우리 공격을 정답이 표시된 사건으로 섞는다.** 단, 같은 파이프라인을 거치게 한다.
> 관련: `03_ML_vs_LLM_비교실험_계획.md`(비교·채점), `04_SOAR_구현계획.md`(대응 데모)

## 0. 한눈에

| 질문 | 결정(안) |
|---|---|
| 정상 데이터는? | **정상 행위 생성기**(랩 안) + **공개 로그**(배경 잡음) |
| 공격 데이터는? | 우리 랩에서 투입, **정답지에 기록** |

## 1. 가장 큰 함정 — 출처가 다르면 ML이 "출처"를 학습한다

공개 데이터(남의 서버)와 우리 공격 데이터(우리 랩)를 그대로 합치면 IP 대역·시간대·로그 형식이 전부 다르다.
그러면 ML은 공격이 아니라 **"이건 우리 랩에서 온 데이터"** 를 구분하게 되고, 결과는 100% 탐지처럼 나오지만 의미가 없다.

**원칙**
1. 공개 데이터와 우리 공격 모두 **같은 파이프라인**(Wazuh → 같은 피처 계산)을 거친다
2. 우리 랩에도 **정상 행위를 섞는다** — 랩 데이터 = 공격, 이라는 구분이 생기지 않게
3. 공격 IP만 특이한 대역을 쓰지 않는다 — IP 대역 자체가 단서가 되지 않게
4. 검증: **IP·시간대 피처를 뺀 모델**로도 탐지되는지 확인 (빼면 탐지가 무너진다면 출처를 학습한 것)

## 2. 공개 데이터 후보

> 라이선스·다운로드 조건·현재 공개 여부는 받기 전에 각 사이트에서 확인.

| 데이터 | 내용 | 정답 표시 | 활용 |
|---|---|---|---|
| **Loghub (LogPAI)** | 실제 서버 로그 모음 (OpenSSH, Linux, Apache 등) | 없음 | SSH 로그를 Wazuh에 다시 흘려 **실제 서버의 배경 잡음**으로 |
| **CIC-IDS2017 / CSE-CIC-IDS2018** (캐나다 UNB) | 네트워크 흐름, 브루트포스·웹 공격·DoS 등 | **있음** | 랩 없이 룰·ML·LLM 성능 바로 비교 |
| **LANL 사이버보안 데이터셋** (미국 로스앨러모스 연구소) | 대규모 기업 인증 로그, 레드팀 공격 표시 | **있음** | 인증 이상탐지 (용량이 커서 일부만) |
| **Security Datasets (OTRF, 옛 Mordor)** | 윈도우 이벤트 로그, 공격 기법별 녹화 | 기법별 | 윈도우 시나리오, Wazuh에 다시 흘려 넣기 |
| **CSIC 2010 HTTP** | 정상/공격 웹 요청 | **있음** | API·웹 공격 시나리오 |
| **SecRepo** | 각종 보안 로그 샘플 | 일부 | 참고·보조 |

⚠️ Loghub의 OpenSSH 로그 같은 실제 서버 로그에는 **인터넷의 실제 공격 시도가 이미 섞여 있을 수 있다.** "정상"으로 단정하지 말고 **배경 잡음**으로 취급하며, 채점은 우리가 투입한 공격(정답지)으로만 한다.

## 3. 합치는 방법

| 방법 | 내용 | 장점 | 주의 |
|---|---|---|---|
| **① Wazuh로 다시 흘려 넣기** | 공개 로그 파일을 Wazuh가 읽게 → 우리 랩 로그와 똑같이 alerts.json | 같은 파이프라인, 함정 최소 | 알럿 시각이 처리 시각으로 찍힘 → 원래 시각은 `full_log`에서 추출 |
| **② 피처 단계에서 합치기** | 각각 "IP × 5분" 피처 표로 바꾼 뒤 합침 | 빠름, 형식에 덜 얽매임 | 두 데이터의 피처 정의가 완전히 같아야 함 |
| **③ 정상 행위 생성기** | 정상 사용자처럼 가끔 로그인·오타·불규칙 간격 접속하는 스크립트를 랩에서 실행 | 랩 안의 "평소"가 생겨 출처 함정 방지 | 너무 규칙적이면 티가 남 → 무작위성 충분히 |

**추천 조합: ③(랩 안 정상) + ①(공개 로그 배경 잡음) + 우리 공격 투입.**
`tools/make_sample.py`가 ③의 아주 작은 버전 — 이를 확장해 실제 랩에서 접속을 발생시키는 생성기로 만든다.

## 4. 추천 시나리오

### 시나리오 1 — 빠른 검증 (랩 없이, 1~2일)

- **데이터**: CIC-IDS2017
- **내용**: 정답이 있으니 Isolation Forest·간단한 룰·LLM을 바로 돌려 탐지율·오탐률 채점
- **목적**: **실험 틀(채점 코드, 비교표)을 먼저 완성** → 랩 데이터가 나오면 같은 틀에 넣기만 하면 됨
- 주의: 네트워크 흐름 피처라 Wazuh 로그 피처와 다름 → "채점 틀 검증용"으로 한정

### 시나리오 2 — SSH 공격 (메인 데모)

- **배경**: Loghub OpenSSH 로그(실제 서버 잡음) + 정상 행위 생성기
- **공격**: 빠른 브루트포스, 느린 공격(룰 임계치 밑), 여러 서버를 넘나드는 공격
- **포인트**: "룰은 침묵, ML은 탐지"를 **실제 서버 잡음 속에서** 재현 → 가상 데이터만 쓸 때보다 설득력 큼
- **연결**: SOAR SSH 브루트포스 플레이북 데모 (`04` §4-1)

### 시나리오 3 — API 대입 조회 (신한 사례)

- **배경**: 기존 FastAPI 실습 랩(`finance_secure` 런북/API대입공격_실습) + 정상 사용자 호출 생성기
- **공격**: 고객번호를 바꿔가며 조회 (빠른 버전, 느린 버전)
- **보조**: CSIC 2010으로 웹 공격 요청 패턴 보강
- **연결**: SOAR API 플레이북 데모 (`04` §4-2)

### 시나리오 4 (선택) — 윈도우 내부 확산

- **데이터**: Security Datasets의 윈도우 공격 녹화를 Wazuh에 다시 흘려 넣기
- **포인트**: 리눅스 SSH와 다른 종류의 공격도 다룬다는 폭

## 5. 팀 분담 — 서버 여러 대, 각자 분석

**원칙: "각자 따로"가 아니라 "각자 맡되 같은 규칙으로".**

| 담당 | 서버 역할 | 주 시나리오 | 담당자 |
|---|---|---|---|
| A | 웹·API 서버 | 시나리오 3 | |
| B | SSH·리눅스 서버 | 시나리오 2 | |
| C | 윈도우 서버 | 시나리오 4 | |
| 공통 | 채점 틀 | 시나리오 1 | |

- **각자 자기 노트북에서** Wazuh + ML 실행 → RAM 문제가 자연스럽게 분산
- 각자 분석(서버별 모델) + 데이터를 모아 분석(통합 모델) → `03`의 **"서버별 모델 vs 통합 모델"** 비교가 그대로 실험 항목이 됨

### 5-1. 공통 피처 표 형식 (초안 — 1주차에 확정)

한 행 = **서버 × 출발지 × 5분 구간**

| 열 | 의미 | 비고 |
|---|---|---|
| `server` | 서버 이름 (web01, ssh01, win01) | |
| `role` | 서버 역할 (api, ssh, windows) | 통합 모델용 |
| `src` | 출발지 IP 또는 계정 | |
| `window_start` | 구간 시작 시각 (UTC, ISO8601) | **원래 이벤트 시각 기준** |
| `events` | 이벤트(알럿) 수 | |
| `auth_fail` | 인증 실패 수 | |
| `uniq_users` | 서로 다른 계정 수 | |
| `uniq_targets` | 서로 다른 대상(호스트·고객ID) 수 | API는 고객ID |
| `err_ratio` | 에러 비율 | |
| `burst_entropy` | 요청 간격 엔트로피 | 낮을수록 기계적 |
| `rule_level_max` | 최고 룰 레벨 | 룰 기반 비교용 |
| `cpu`, `net_tx`, … | 모니터링 지표 (선택) | Prometheus 연동 시 |
| `source` | 데이터 출처 (lab / loghub / …) | **모델 입력에서 제외**, 분석용 |

- 서버마다 해당 없는 열은 0이 아니라 **빈 값**으로 두고, 모델별로 사용할 열을 명시
- 계산 코드는 **하나의 공통 스크립트**로 (각자 따로 짜면 정의가 미묘하게 달라짐)

## 6. 진행 순서

| 주차 | 내용 | 산출물 |
|---|---|---|
| 1주차 | 공통 피처 표·정답지 형식 확정 + 시나리오 1로 채점 틀 완성 | 형식 문서, `build_features.py`·`score.py` (예정) |
| 2주차 | 각자 서버를 맡아 정상 행위 생성기 + 공개 로그로 배경 데이터 생성 | 서버별 배경 데이터 |
| 3주차 | 공격 투입 → 서버별 분석 → 통합 분석 → 비교표 | 결과 표, SOAR 데모 |

## 7. 주의

- 공격은 **각자 통제하는 랩 안에서만**. 같은 공유기·와이파이의 다른 기기를 건드리지 않게 대상 IP를 정답지에 명시.
- 공개 데이터는 **각 데이터의 이용 조건**을 지키고, 원본 재배포가 금지된 경우 저장소에는 다운로드 방법만 적는다.
- 큰 데이터 파일은 Git에 올리지 않는다 (`data/`는 `.gitignore`).
